## 5.6 + 5.7：解析移出 UI isolate + 真实进度 + 可取消（已完成）

commit 序列：`676d1ee`（阶段回报）→ `ce87b22`（isolate + 取消 + UI）

### 新增 `lib/apkparser/parse_task.dart`
- `ApkParseTask.start(path)` 派生 worker isolate；`task.events` 是有序 `Stream<ParseEvent>`；`task.cancel()` 是**真正终止**。
- 事件：`ParseStageReached` / `ParseOpenFailed` / `ParseFailed` / `ParseSucceeded` / `ParseCancelled`。
- `ParsedApkData { ApkMeta meta, Map<int, ResourceInfo> arscResources }` 跨 isolate 传递。
- **图标渲染留在主 isolate**：`ApkInfo` 持有 `dart:ui` 的 `Image`，不能跨 isolate 传。worker 只做纯计算（那正是卡 UI 的部分）。

### 关键取舍
- 取消用 `Isolate.immediate`，不是默认的 `beforeNextEvent` —— 后者要等 worker 回到事件循环，
  而 worker 绝大部分时间耗在一段同步 arsc 解析里，那恰恰是用户想取消的时刻。
  代价：立即终止不执行 `finally`，因此 **worker 内禁止创建临时文件/持有需显式释放的资源**（代码里写明了）。
- 进度只报阶段、**不报百分比**：各阶段耗时极不均匀，百分比是编的。
- XAPK/aapt2 路径仍走 `Process.run`，**不可取消** → 该路径下不显示取消按钮
  （未实现的功能不得出现伪可用按钮）。
- 取消 ≠ 失败：`ApkParseCancelledException` 单独成类型，UI 不弹错误提示。

### 测试经验
- 先用**探针测试**确认 `Isolate.spawn` 的 async 入口能跨越 await（三条消息都收到），
  再基于该结论实现 —— 避免把设计建立在猜测上。
- 取消测试用一个 4 MiB 条目，保证 worker 在 `cancel()` 时**确实还在忙**，
  否则测的是「取消已完成的任务」这种无意义场景。

### 分工：静态提取 vs 验证
规范 5.5 禁止自行实现签名算法并宣称权威结论，因此**包内只做静态提取**：
- `packages/ipa_parser` 回答「文件里有什么」；
- `lib/utils/ios_codesign_analyzer.dart` 回答「是否有效」，且**只以 `--verify` 退出码为准**。

`codesign -d` 的输出是**描述性信息**，不是结论 —— 实测确认它对一个签名已损坏的
bundle 照样退出 0 并打印内容。

### 三个必须区分的结论
- 有材料但没跑过工具 → `toolUnavailable`（显示「无法确认」）
- 连材料都没有 → `unknown`（**不是**「无效」，更不是「恶意」）
- 描述文件读不出来 → `FieldStatus.failed`（**不是** `absent`；那会把「读不到」说成「没有」）

### 踩到的真实行为（都写进了代码注释与审计文档）
1. **BER 不定长容器的 EOC 只能消费一次**。把「内容结束」与「本元素结束」混为一谈，
   父容器读到子元素的 EOC 时会误以为自己也结束了。真实描述文件的 `eContent` 后面
   还有证书与签名者信息 —— 提前收尾会解析出**被截断的 plist**（字段都在、长度不对，
   极难发现）。`_Tlv` 因此区分 `contentEnd` 与 `nextOffset`。
2. `codesign --verify` 退出码 **3** = 「密封完好但不满足指定要求」（ad-hoc 必然如此）。
   把非 0 一律读成「签名无效」会把正常的 ad-hoc 重签包说成被篡改。
3. **只认退出码会凭空报出「签名有效」**：路径指向 `/usr/bin/true` 也返回 0。
   因此退出码 0 还要求输出里出现 codesign 特有结论行。
4. `codesign -d --entitlements :-`（带冒号）才是原始 XML plist；裸 `-` 是人读格式。
   前者已被标记将来移除，所以解析失败只记「没读到」，不当成「没有授权项」。
5. `Sealed Resources version=2 rules=13 files=74` —— 键与等号之间还有内容。
   按「第一个等号」切分会得到假键，该字段永远为空。
6. **`git ls-files` 会漏掉未 `git add` 的新文件**，本地门禁通过、CI 才红。
   本次实际踩到三处。CI 与本地一律改用 `git ls-files -co --exclude-standard`。

### 授权比对
`application-identifier` = `<App ID 前缀>.<bundle id>`，`CFBundleIdentifier` 只有
`<bundle id>` —— **必须按后缀比较**。直接比字符串会让每一个正常应用都被判成
「授权的是别的应用」。通配符的结论是「覆盖」而非「确认」。

### 解包
`codesign` 需要磁盘上的 `.app`，所以必须解包。做法：先算后写（超限不写盘）、
逐条 `ZipGuard.safeJoin`、声明尺寸与实际不符即中止、按实际字节兜总量、
**不创建符号链接**（链接目标可以是 `../../..`）、取消与任何失败都清理临时目录。

## 把 AXML 非标准布局变成加固线索

### 做了什么

| 事实 | 标准值 | 实测加固样本 |

2. **必须做误报防护**。新增 `test/fixtures/apk/standard-manifest.axml`：
   手工构造的 196 字节最小标准 AXML，检测对它一条都不报。
   没有这条反向用例，检测很容易变成「看到什么都报」。

用户要求「打包一个最新 MAC 版本 APP，注意签名问题」。**本机做不到**，

| 前置 | 实测证据 |
|---|---|

| CocoaPods | `pod not found` —— 本项目有 **8 个** macOS 原生插件（`GeneratedPluginRegistrant.swift` 里 import 了 desktop_drop / file_picker / package_info_plus / path_provider_foundation / screen_retriever_macos / shared_preferences_foundation / url_launcher_macos / window_manager），必须经 CocoaPods 集成 |

**手工绕过 Xcode 不可行**：`GeneratedPluginRegistrant.swift` 直接 `import desktop_drop`
等模块，没有 CocoaPods 就链接不上，做出来的 app 一跑插件注册就崩。

用户选择「你装 Xcode + CocoaPods，我来出包」。因此先交付：

- `tool/build_macos.sh` —— 前置检查放最前（缺什么直接给出确切修复命令），
  构建 → `codesign --verify --strict` 校验 → **打印签名种类** → 按 CI 约定打包
  （create-dmg 出 DMG，否则 ditto 出 zip）。
  已实测：现在跑会在 Xcode 那步停下并打印 `sudo xcode-select --switch ...`。
- `docs/delivery/macos-build-and-signing.md` —— 三种签名级别的适用范围、
  工程现状、以及**CI 目前完全没有签名与公证步骤**这一事实。

### 关键事实：签名
- 工程里 `CODE_SIGN_IDENTITY[sdk=macosx*] = "-"` 已经是 **ad-hoc**，本地自用够。
- ad-hoc 的产物**拷到别的 Mac 会被 Gatekeeper 拦**，需右键打开或去 quarantine。
- 正式分发要 **Developer ID Application 证书 + notarytool 公证 + stapler 装订**，
  本机 0 个身份，做不了。
- **CI 的 build-macos 任务只做 `flutter build macos --release` + `create-dmg`，
  没有 codesign（Developer ID）也没有 notarytool** —— 所以 CI 产出的 DMG 是
  ad-hoc、未公证的。这是需要用户决策的点，已写进文档。

### 顺带核实的沙盒约束
`ToolPaths.appSupportDir` 用 `getApplicationSupportDirectory()`，macOS 沙盒下会把
`~/Library/Application Support/<bundle-id>` **自动重定向到容器内**，所以下载目录
默认值安全；但用户若把 `Config.downloadDir` 设成容器外的绝对路径会被拒。
另外：`apkByArgs`（命令行参数）在沙盒下拿不到文件权限 —— Finder 双击/拖放/选择
文件这三条路不受影响。**这两条都尚未实测**，首次出包后要专门验证。

## 换 LOGO + 应用名改为「APP详情工具」

### 图标：写成脚本而不是手工跑命令
源图 1254×1254，要产出 **4 处 / 10 个文件**，格式还不一样：
- macOS `AppIcon.appiconset` 7 张 PNG（16/32/64/128/256/512/1024）
- Windows `app_icon.ico`（48/64/96/128/192 BMP + 256 PNG）
- `assets/image/icon.png`（256，关于对话框用）
- `docs/assets/icon_512.png`（512，README 用）

→ 新增 `tool/generate_icons.py`。**只依赖 macOS 自带的 `sips`**（本机无 Pillow、
无 ImageMagick）。缩放交给 sips，ICO 自己拼 —— sips 不产出 ICO，而 ICO 格式足够
简单，与其为此引入图像库不如把格式写清楚。

**ICO 的验证方式**：不是「跑完没报错」，而是把 ICO 里的 BMP 条目**解回来渲染成
PNG 肉眼确认**颜色与内容。手写的二进制格式只有看回来才算验过。
另外各条目字节数与仓库原有 ICO 逐一相同（9640/16936/38056/67624/152104），
这是结构正确的强信号。

**踩到的坑**：`sips -s format bmp` 输出的是 **24 位、负高度（自上而下）** 的 BMP。
ICO 里需要的是 **32 位、正高度（自下而上）+ AND 掩码**，两者必须显式转换。

### 应用名
`APK Info Tool` → `APP详情工具`，覆盖：6 个语言的 i18n `title`、
macOS `PRODUCT_NAME` + `CFBundleDisplayName`、Windows 窗口标题与 rc 资源、
Linux GTK 标题与 AppImage 的 desktop `Name=`、**Xcode 工程的硬编码引用**
（pbxproj 的产品路径与 `TEST_HOST`、xcscheme 的 `BuildableName`）、
构建脚本与 CI 的产物路径 / DMG 卷名、中英 README。

**刻意保留 ASCII**：`pubspec.yaml` 的 `name: apk_info_tool`（Dart 包名，改了
所有 `package:apk_info_tool/...` 导入都会断）、Windows/Linux 的 `BINARY_NAME`
（中文 exe 名在 rc/CMake 里易出编码问题，且用户可见名已由窗口标题与文件属性承担）、
bundle id、Linux `APPLICATION_ID`。

### 关键判断
改 `PRODUCT_NAME` 必须同步 Xcode 工程里硬编码的 `apk_info_tool.app`。
实测确认：**Runner.xcscheme 的 BuildAction 只构建 Runner**，RunnerTests 在

## macOS 构建：环境两条路都被堵住（用户已装 Xcode）

用户装好 Xcode 27.0 后第一次尝试构建。**结论：在自动化执行环境里跑不通，
但与工程本身无关。**

### 实测到的事实
| 项 | 结果 |
|---|---|
| Xcode | 27.0，`xcode-select -p` 正确指向 Xcode.app ✓ |
| CocoaPods | 未装（用户没装） |
| Homebrew | **不存在** → 装不了 Ruby 3 |
| 系统 Ruby | 2.6.10 |

### 两条路都堵住
1. **SPM（Flutter 3.47 的默认路径）**：`swift package resolve` 报
   `sandbox-exec: sandbox_apply: Operation not permitted`。
   **决定性判断**：`sandbox-exec -p '(version 1)(allow default)' /usr/bin/true`
   能过，而 `-p '(version 1)(deny default)(allow file-read*)'` 被拒 →
   我的执行环境只允许「不比自身更严」的嵌套沙箱，SPM 用的严格 profile 过不去。
   **这是我这边的限制，用户在普通终端里不受影响。**
   另外 `dangerouslyDisableSandbox` 在本会话**无效**（实测 `ps` 仍被禁）。
2. **CocoaPods（退路）**：`gem install --user-install cocoapods` 在 Ruby 2.6 上
   失败。逐层钉住版本（securerandom 0.3.2 / drb 2.0.6 / i18n 1.14.8 /
   zeitwerk 2.6.18 / activesupport 6.1.7.10 / cocoapods 1.16.2）后**装上了**，
   但运行 `pod --version` 报
   `uninitialized constant ActiveSupport::LoggerThreadSafeLevel::Logger`
   —— Ruby 2.6 + activesupport 6.1 的已知不兼容。**此路不通。**

### 顺带修掉三个真问题
1. **构建脚本硬性要求 CocoaPods** —— 会把一条本来能走通的路堵死（Flutter 默认
   用 SPM）。改成缺 CocoaPods 时只打印说明并继续。
2. **`ok "Xcode（$DEV_DIR）"` 的全角右括号被 bash 算进变量名**，报
   `DEV_DIR）: unbound variable`。这个 bug 一直是潜伏的：之前 Xcode 没装，
   走的是另一个分支。已改 `${DEV_DIR}`，并写了个正则扫全脚本确认无同类写法。
3. **采纳 Flutter 的迁移**：部署目标 10.14 → 12.0（Podfile + pbxproj 三处）；
   `AppDelegate` 补 `applicationSupportsSecureRestorableState`。
