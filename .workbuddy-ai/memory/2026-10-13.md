## 第二步前半：解析安全与可诊断性（已完成）

commit 序列：`a157b97` → `6830e73` → `4a59a6a`

### 5.3 ZIP 预算下沉为单一实现
- 新增 `packages/apk_parser/lib/src/zip_budget.dart`：`ZipBudget`（4 个阈值 + `isExceeded` + `ensureWithin`）
  与 `ZipBombException`（独立类型，便于区分「安全拒绝」与「解析失败」）。
- `lib/utils/zip_guard.dart` 删除重复的预算逻辑，只保留路径级防护（`safeJoin` + `extractToDirectory`）。
- `tool_downloader.dart` 改调 `ZipBudget.ensureWithin`。

### 5.4 归档打开失败原因可区分
- 新增 `packages/apk_parser/lib/src/archive_open.dart`：
  `enum ArchiveOpenResult { ok, notArchive, corrupt, resourceBudgetExceeded, ioError }`（含 `isOk` / `description`）
  + `looksLikeZip()` + `readArchiveHeader()` + `looksStructurallyBroken()`。
- `ApkReader.open/openBytes`、`ZipHelper.open` 由 `bool` 改为返回该枚举，全部调用点已更新。
- `getApkInfo` 改抛 `ApkOpenException(result, filePath)`（archive 分支与 builtin 分支）；
  `_getApkInfoBuiltin` 用 `on ApkOpenException { rethrow; }` 防止被兜底 catch 吞掉。
- `info_page._describeOpenFailure()` 映射到 6 语言的新 i18n key
  `parse.open_failure_{not_archive,corrupt,budget,io}`。

### ⚠️ 新发现的真实行为（重要）
**本仓库使用的 archive fork 对「有 ZIP 魔数但结构损坏」的输入不抛异常，而是返回空归档。**
若不额外判断，损坏文件会被判为打开成功，直到找不到 `AndroidManifest.xml` 才失败。
已用 `looksStructurallyBroken(archive, inputLength)` 兜住（空解码 + 输入长于 22 字节 EOCD → corrupt）。

### 5.11 InstallDialog 的 mounted 守卫
- 补齐 8 处 await 后的 `setState`（`_loadDevices` try+catch、`_loadSplitApks`、
  `_installApk` 循环 4 处、`_showStopConfirmDialog`）；安装循环在 `!mounted` 时也 break。
- 为可测试性给 `InstallDialog` 加了可选 `deviceLoader` 参数（默认仍走真实 `adb devices -l`，
  已抽出为 `_queryAdbDevices`）。

### 测试经验（踩坑记录）
- **反向验证是必须的**：我先后写了 3 版生命周期测试，前两版「移除守卫后仍然通过」——
  第一版因为 `Process.run` 是真实 I/O，fake clock 推不动，await 后的代码根本没执行；
  第二版因为 `try` 里的守卫拦住了，`catch` 根本进不去。

- 手写 ZIP EOCD 极易写错长度（我第一版只写了 20 字节，应为 22），
  用 `ZipEncoder().encode(Archive())` 生成空归档更可靠。
