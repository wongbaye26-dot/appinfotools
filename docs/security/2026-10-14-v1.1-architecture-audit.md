# V1.1 安全检测引擎 — 阶段一：架构核查报告

日期：2026-10-14  ·  规格来源：《AppInfoTool 下一版本开发说明》
结论先说：**不需要推倒重来**。原有四层结构（archive_safety / analysis_model /
apk_parser+ipa_parser / 应用层编排）与规格第六章的「不重写既有解析器」完全相容。
本版本要新增的是**一套平台中立的发现项模型 + 两个平台各自的审计器 + 一个规则引擎**，
原有代码只做**加法式扩展**。

## 三、规则引擎口径（与规格第五章一一对应）

- **等级**：P0–P3 / INFO / UNKNOWN，`rank` 可比较；等级由「证据强度 × 业务合理性 ×
  数据敏感度 × 用户参与方式 × 数据流关联度」共同决定，**不由权限数量决定**。
- **四态关联**（规格 7.3）：`confirmed`（同一可追踪路径或权威工具）/
  `suspected`（多线索同现，未证实数据流）/ `independentCapability`（仅发现独立能力）/
  `unknown`（加固、混淆、解析失败）。
- 规则 A–F 全部实现，其中 **E 的关键前提是「多项相互印证」**：只有「后台任务 +
  敏感数据 + 回传」三类证据同时存在才升级，且措辞必须是「需运行时验证」。
- **规则 F 必须显式输出**：没找到上传特征时，报告里要写「当前分析范围内未发现
  相关特征」，**绝不写「确认安全」**。
- 每个 finding 都带 `evidence[]`（来源 + 位置 + 原文），没有证据的字段留空或
  标 UNKNOWN。

## 四、测试计划

1. **模型层**：等级排序、四态映射、JSON 往返（阶段四导出依赖）、
   「空 findings 不出高风险结论」。
2. **权限目录**：`maxSdkVersion` 修正（真实加固夹具：`READ_EXTERNAL_STORAGE`
   带 32 限定时，在 targetSdk=34 上必须降级为 INFO 而不是 P2）；
   `READ_MEDIA_VISUAL_USER_SELECTED` 不得与完整图库访问混为一类；
   未知权限不逐条刷屏（汇总一条 INFO）。
3. **DEX 扫描器**：预算截断要如实进 limitation；域名/上传/OCR 标记各有 evidence；
   空输入、非 DEX 内容、超大文件三条边界。
4. **规则**：A（仅广泛存储→P2，不判恶意）、B（相册+OCR→P2 且措辞为「可能」）、
   C（+上传→P1 suspected 且列出未证实环节）、D（明文+敏感→P1）、
   E（缺任一项不得升级）、F（无上传→输出「未发现」措辞）。
5. **iOS**：PHPicker（用户主动选择）与 PhotoKit（完整库）必须区分；
   有 PhotoKit 线索但缺用途说明 → P2；xcprivacy 存在 → INFO 且注明是声明性材料。
6. **反向验证**：把规则条件逐个关掉，确认对应测试真的变红。
7. **真实样本回归**：`APPINFOTOOL_SAMPLES` 下的加固 APK 与签名 IPA 端到端
   （原有 real_samples 两件套继续全绿）。

## 五、已知取舍（写进代码注释，不粉饰）

- 字符串扫描**不做反汇编、不还原调用图**：规则 B/C/E 的「疑似」全部来自
  多标记同现，不是数据流证明 —— 措辞与 limitation 必须始终这么说。
- ASCII 字符串提取会漏掉非 ASCII 字面量（中文域名、本地化字符串），
  作为 limitation 声明。
- DEX 扫描设 8 MiB/文件的预算（超大 DEX 截断并记录），不做全量物化。
- iOS 只扫主 Mach-O 可执行文件的字符串；Frameworks / dyld 共享缓存不扫（记录为未覆盖）。
