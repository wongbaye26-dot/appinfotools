## 1. 解析速度：64.1 秒 → 13.5 秒（4.75×）

### 1.1 样本与基线

样本：用户给的 `抖音-v40.7.0.apk`（**343.2 MB**、47,090 个条目、55 个 `classes*.dex`）。

探针：`tool/perf_probe_apk_test.dart`（**不进质量门禁**；样本路径可用
`PERF_APK` 环境变量覆盖）。

**优化前**（逐段计时，单位 ms）：

```
1. 打开归档（中央目录 + 预算 + EOCD）                  369.1
2. parse（manifest + arsc + 原生码）                     98.2
3. 资源表全量遍历（178724 项）                            50.6
4b. 读取全部 DEX 字节                                   925.2
5b. 读取选中的原生库字节                                  41.8
6. 加固线索扫描                                          30.1
7. 容器结构统计                                          11.2
8a. 审计·DEX 字符串扫描                                1931.3
8b. 审计·DEX 结构（55 个）                              554.7
8c. 审计·方法引用与调用点遍历                         60588.7   ← 92%
8d. 审计·原生符号扫描                                    15.1
8. 安全审计（DEX + 原生符号）                          62645.1
9. 资源引用环检测                                         6.4
★ 端到端（open → 审计 → 环检测）                       64100 左右
```

**结论先行**：整条链路上**只有一个热点** —— 安全审计里的
`DexMethodScanner.scan`（方法引用与调用点遍历）占 60.6 秒。其余所有阶段
加起来不到 2 秒。

### 1.2 热点内部再拆一次

| 项 | 耗时 |
|---|---|
| 仅遍历 `method_ids`（**2,879,590** 条） | 1.0 s |
| 仅遍历调用点（**15,863,165** 个） | 3.2 s |
| 两者 + 标记匹配（现状） | **60.6 s** |

也就是：**遍历本身只要 4.2 秒，剩下 56 秒全花在标记匹配上** ——
18,706,755 次 `matchCodeMarkers`，每次跑 23 个标记 × 2 次子串搜索。

### 1.3 改动一：调用点按 `method_idx` 查表（60.6 → 12.9 s）

**关键事实**：`invoke-*` 指令的操作数**就是** `method_idx`，而它指向的正是
`method_ids` 里刚看过的那一条。因此「这个调用点命中哪些标记」不需要重新拼
字符串、重新匹配 —— 第一遍记下「下标 → 命中的标记」，第二遍查表即可。

- `DexMethodReference` 增加 `index` 字段（`method_ids` 下标）；
  `DexMethodTable.forEachReference` 与 `DexMethodBodies.walk` 各自填上。
- `DexMethodScanner` 建 `Map<int, List<CodeMarker>>`，调用点用 `site.target.index` 查。

**精确性**：唯一可能不一致的情况是 `method_ids` 那一遍**被预算截断**
（`maxReferenceEntries = 200_0000`）—— 此时下标查不到表。代码里显式处理：
只有 `referenceResult.truncated` 时才退回完整匹配。本样本每个 DEX 的
`method_ids` 都远低于预算，走不到那条分支。

### 1.4 改动二：16 个标记只需要比一次（12.9 → 10.5 s）

`matchCodeMarkers` 原本对每个标记都比两次（原文 + 把 `/` 换成 `.` 的归一化
文本）。但归一化**只把 `/` 换成 `.`**，因此：

- 字面量**既不含 `/` 也不含 `.`** 的标记（23 个里有 16 个）：归一化既不会
  凭空造出匹配、也不会破坏原有匹配 —— **比一次就够**；
- 含 `/` 的标记（`multipart/form-data`）：归一化之后 `/` 已不存在，
  **只可能命中原文**；
- 含 `.` 的标记（7 个）：原文与归一化文本都要比。

另加两处小改：没有 `/` 时不调用 `replaceAll`（省一次分配）；没命中时返回
`const []`（这个函数会被调用几百万次）。

### 1.5 结果

```
8a. 审计·DEX 字符串扫描                           1714.3
8b. 审计·DEX 结构（55 个）                        549.6
8c. 审计·方法引用与调用点遍历（现状）                  9970.4
8. 安全审计（DEX + 原生符号）                    12238.8
★ 端到端（open → 审计 → 环检测）                  13489.1
```

**端到端 64.1 s → 13.5 s，4.75×。**

### 1.6 剩下的 10 秒在哪 / 为什么不再往下压

| 项 | 约 |
|---|---|
| `method_ids` 遍历 + 标记匹配 | 6.2 s |
| 调用点遍历（1586 万个） | 3.2 s |
| DEX 字节读取（约 100 MB） | 0.9 s |
| 字符串扫描 / 结构 / 其余 | 2.5 s |

- **「按类缓存描述符的匹配结果」** 能再把第一项压到 2～3 秒（`method_ids`
  按类排序，同一个描述符下跟着成百上千条引用）。**没做**：它的精确性依赖
  「标记跨过 `描述符 + '.' + 方法名` 那个连接点时必然含 `.`」这一条论证，
  为 3 秒收益引入一处需要逐字证明的分支不划算。
- **按 DEX 文件并行**（10 核，理论上 5～8×）**没做**：扫描跑在
  `ApkParseTask` 的 worker isolate 里，而取消用的是 `Isolate.immediate` ——
  杀掉 worker **不会**杀掉它派生的子 isolate，那些 isolate 会继续烧 CPU 到
  自己跑完。要并行就得先重排取消语义，风险大于收益。
- **调用点那一遍的字符串构造**（每个调用点都 new 一个 `DexCallSite` +
  `DexMethodReference`，1586 万次）还能再省一点，但 3.2 秒里占比不大。

## 2. ICP 备案号

### 2.1 它在包里到底在哪（先验证，再实现）

写代码之前先用 python 把几个真实 APK 的 `resources.arsc` 与 `classes*.dex`
扫了一遍：

| 样本 | 结果 |
|---|---|
| `抖音-v40.7.0.apk` | `resources.arsc` 字符串池里有一条独立的 **`京ICP备16016397号-49A`** |
| `飞牛-v1.37.1.apk` | 无 |
| `澳門上葡京-v6.9.76.apk` | 无 |
| `181_1014020007.apk` | 无 |
| `214_0901215006.apk` | 无 |

**结论**：`AndroidManifest.xml` 里没有标准字段，但备案号几乎总会以**字符串
字面量**的形式落在 `resources.arsc` 的字符串池里 —— 那是唯一一个不依赖各家
实现的位置。而**大部分应用没有** —— 所以界面必须「取不到就不显示」。

### 2.2 实现

- `packages/apk_parser/lib/src/icp_filing.dart`：`IcpFilingScanner`。
  - `scanValues(Iterable<String>)` 是纯函数部分（**为了可测** —— 造一个
    `StringPool` 需要一份真实的 arsc，而「哪些写法算备案号」恰恰最需要钉住）；
  - `scan(StringPool?)` 是 arsc 适配层，先 `contains('ICP')` 预筛再跑正则
    （抖音的字符串池有二十多万条，逐条跑正则纯属浪费）。
- `ArscParser.globalStringPool`：暴露全局字符串池（此前是私有的）。理由是
  「从字符串池里找某个事实」的检查不该自己再解一遍 arsc。
- `ApkMeta.icpFilings` → `ApkInfo.icpFilings` → `AndroidPackageInfo.icpFiling`
  （`FieldValue<String>`，多条时换行连接）→ 分析页「概览 → 应用信息」里渲染，
  **`absent` 时整行不显示**。

### 2.3 正则的两个坑（都写进了测试）

- **省份简称必须逐个列出**，不能写 `[\u4e00-\u9fa5]{0,1}`：后者在前一个汉字
  不是简称时会把那个字一起吃进来 —— 实测 `备案ICP备2021000000号` 会匹配成
  `案ICP备2021000000号`。列的是 31 个省级简称（另收繁体写法，港澳台应用会
  写成 `粵ICP證…號`）。
- **空格容错只吃半角与全角空格**，不用 `\s`：那会连换行一起吃掉，让跨行的
  两段文字被拼成一个假的备案号。

### 2.4 已知局限（写进代码注释与 CHANGELOG）

- 只覆盖**字符串池**。写在 DEX 里、或运行时从服务端下发的备案号看不到 ——
  这类应用会显示成「没有」。
- **不做合规判定**：只回答「包里写了什么」，不回答「写的是不是真的 / 有没有
  过期」—— 那需要查工信部的库，不是静态解析能做的。

### 2.5 验证

- 单元测试 `packages/apk_parser/test/icp_filing_test.dart`：**15 条**
  （正例 9 条含全部省级简称、反例 6 条）。
- **端到端**（真实包，临时探针，跑完即删）：


## 4. 概览页「详细信息」只显示 6 项

**保留**（顺序即优先级）：

| # | 字段 | 理由 |
|---|---|---|
| 1 | 文件名 | 用户拖进来的就是它 |
| 2 | 版本 | 最常被比对 |
| 3 | 构建号 | 与版本配套 |
| 4 | 最低系统（minSdk / minOS） | 「能不能装在这台设备上」 |
| 5 | SHA-256 | 现在的通用口径，最常被复制 |
| 6 | targetSdk（Android）/ 可执行文件名（iOS） | 各自平台最有用的第 6 项 |

**去掉的是 SHA-1 与 MD5** —— 它们只在需要与旧记录比对时才有用，而在**分析页
与导出的报告里仍然都在**。不是删掉能力，只是不占概览页这块地方。

**顺带修掉一个真实缺陷**：网格此前最多 8 项（3 行），而这一块的高度没有算进
固定一屏的预算（`_chromeHeightEstimate` 是估算值）。收到 6 项（2 行）之后
**满 6 项**时默认窗口（1040×800）仍溢出 **1px** —— 新增的测试直接抓到了。
按本项目一贯做法**动间距、不动内容**：状态卡片与网格之间的间距 14 → 12
（紧凑 12 → 10）。
