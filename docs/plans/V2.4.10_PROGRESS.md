# AppInfoTool V2.4.10 — 「已拒绝打开：归档超出安全解压上限」

> 用户报：`49af6cnn-1018.apk`（71.0 MB）解析不了，提示「已拒绝打开：归档超出
> 安全解压上限」。
>
> 结论：**不是误报的解析器 bug，是安全预算误伤了一类真实的加固包**。
> 已修复，修复后 226ms 解析完成。

---

## 1. 这个包到底哪里超了

| 项 | 值 | 预算 |
|---|---|---|
| 条目数 | 4,075 | 100,000 ✓ |
| 声明解压后总量 | 243.2 MiB | 1 GiB ✓ |
| **`AndroidManifest.xml`** | **75,807,232 字节（72.3 MiB）** | 单条目 256 MiB ✓ |
| 它的压缩后大小 | **368,927 字节** | — |
| **它的压缩比** | **205:1** | **上限 100:1 ✗** |

所以命中的是**压缩比**规则（`uncompressed > 16 MiB && ratio > 100`）。

## 2. 那 72 MiB 是什么

拆开看：

```
@        0  type=0x0003  headerSize=8   size=75807232     ← 根 chunk（AXML）
@        8  type=0x0001  headerSize=28  size=75772552     ← 字符串池（72.2 MiB）
@ 75772560  type=0x0180  ...                             ← 真正的 XML 从这里开始
```

- **字符串池占了 72.2 MiB，其中 99.7% 是 0x00**（前 12 MiB 全零、中间 48 MiB 全零）；
- **真正的 XML 只有末尾约 35 KB**（86 个元素）。

这是**刻意的反分析填充**：把一个合法的、可解析的清单膨胀到 72 MB，专门用来
打断「按体积或压缩比设阈值」的工具。而它恰恰是本工具该分析的样本。

## 4. 为什么不能只调阈值

第一反应是「把 100:1 提到 1000:1，只拒绝纯零填充」。**实测行不通**：

| 数据 | deflate 后 | 压缩比 |
|---|---|---|
| 17 MiB **纯零**（`archive` 包的 `ZipEncoder`） | 77,916 | **229:1** |
| 这个被填充的 `AndroidManifest.xml` | 368,927 | **205:1** |

**229 与 205 几乎一样。** 压缩比区分不了「零填充的合法文件」和「零填充的炸弹」——
因为两者在物理上就是同一种东西。

（顺带纠正一个我一开始的错误假设：python 的 zlib level 9 对纯零能给 1029:1，
但 `archive` 包用的是自己的 deflate 实现/等级，只有 229:1。**不能拿别的工具的
压缩比去推本工具的行为。**）

## 5. 改法：只看绝对大小

真正决定风险的是**解压后要占多少内存**：

- 72 MiB 的清单读进来毫无压力（实测解析 226ms）；
- 1 GiB 的展开无论压缩比多少都该拒绝。

因此 `ZipBudget` 去掉压缩比规则，只留两条绝对上限（**都没动**）：

```dart
static const int maxSingleEntryUncompressed = 256 * 1024 * 1024;  // 单条目
static const int maxTotalUncompressed      = 1024 * 1024 * 1024;  // 总量
static const int maxEntryCount             = 100000;              // 条目数
```

去掉压缩比**不改变最坏情况**：1 GiB 的总量上限本来就兜住了，而「1 GiB 的
APK 文件」用随机数据填充也能达到同样的展开量（压缩比 ≈1）。压缩比只是拦住了
**便宜的**版本，代价是把最可疑的样本挡在门外。

### 顺带：拒绝时说清是哪一条

原来只有一句「归档超出安全解压上限」，排查时毫无帮助。`ZipBudget.check` 现在
返回结构化的 `ZipBudgetViolation`（条目名 + 原因），异常消息里带上它：

```
Refusing to open archive: classes.dex: declares 314572800 bytes, over the
per-entry limit of 268435456
```

## 7. 已知取舍

| 项 | 说明 |
|---|---|
| 单条目 250 MiB 从 1 MB 压缩而来 | **会**被接受（旧规则拒绝）。这是有意的：250 MiB 是 256 MiB 上限之内的可承受量 |
