# Windows 真机验收：手测步骤

> 面向：有一台 Windows 10/11 的验收者
> 前置：CI 的 Windows job 已绿（编译通过）；本清单验的是**运行时行为**
> 预计耗时：40–60 分钟（含失败场景）
> 相关：`docs/plans/V2.5.0-windows-thumbnail-implementation.md`

---

## 0. 先读这一段：什么已经自动验过了

下面这些**不需要你手点**，CI 每次都会验：

| 已验证 | 怎么验的 |
|---|---|
| C++ 能编译、DLL 能链接 | `flutter build windows` |
| DLL 与 helper 都进了 `runner/Release` | 构建后 `test -f` + `ls` |
| 安装包能生成 | `inno_bundle` |
| 两个不同 APK 出**不同**图标 | `thumbnail_selftest` 比像素哈希 |
| 自适应图标的包被**拒绝**（不是给半张图） | 同上 |
| 无图标声明的包被拒绝 | 同上 |
| 坏文件被拒绝且**不崩** | 同上（退出码 1，不是崩溃码） |
| 同一包两次提取结果一致 | 同上 + 单元测试 |

**你要验的是剩下这些**——它们依赖真实的 Explorer、注册表与系统缓存：

1. 注册是否生效、Explorer 是否真的调用我们；
2. 系统缓存 / 图标视图的各种设置；
3. 安装、升级、移动、卸载；
4. 失败时 Explorer 是否**不崩**。

## 1. 准备

### 1.1 装包

1. 从 CI 的 `windows-release` artifact 或 Release 页下载安装包；
2. 安装（默认路径即可，**记下安装路径**，后面要用）；
3. 确认安装目录里有这三个文件：

   ```
   apk_info_tool.exe             ← 主程序（BINARY_NAME，见 windows/CMakeLists.txt）
   appinfotool_thumbnail.dll      ← 缩略图处理器
   app_icon_extractor.exe         ← 图标提取器（AOT）
   ```

   缺任何一个都直接记为**失败**，并记录缺的是哪个。

### 1.2 准备测试文件

建一个空文件夹 `D:\thumb-test\`，放进去：

| 文件 | 从哪来 | 预期 |
|---|---|---|
| `a.apk` | 任意真实 Android 应用（如从 APKMirror 下一个） | 显示该应用图标 |
| `b.apk` | **另一个**应用 | 显示**不同**的图标 |
| `c.apk` | `test/fixtures/apk/icon-adaptive.apk`（仓库里） | 无缩略图，显示通用文件图标 |
| `d.apk` | 随便一个文本文件改名成 `.apk` | 无缩略图，**Explorer 不崩** |
| `e.ipa` | 任意真实 IPA（有 PNG 图标的那种更稳） | 显示 iOS 应用图标 |
| `f.ipa` | 另一个 IPA | 显示**不同**的图标 |

> `b.apk` 与 `a.apk` 一定要是**不同应用**，否则「显示了不同图标」这件事证明不了。

### 1.3 设定视图

在 `D:\thumb-test\` 里：

- 右键 → **查看 → 大图标**；
- 右键 → **查看 → 显示 → 取消勾选「始终显示图标，从不显示缩略图」**
  （Windows 11 在「查看 → 显示」里；Windows 10 在「文件夹选项 → 查看」里）。

## 3. 失败与安全（这几条最重要）

Explorer 扩展最常见的故障是「带崩桌面」。下面每条都要**确认 Explorer 还活着**。

| # | 操作 | 预期 | 记录 |
|---|---|---|---|
| 15 | 关掉 AppInfoTool，把 `app_icon_extractor.exe` 改名 | 缩略图消失（通用图标）；**Explorer 正常** | ☐ |
| 16 | 恢复文件名 | 缩略图回来 | ☐ |
| 17 | 把 `app_icon_extractor.exe` 换成一个**会卡住**的程序（见 §3.1） | 1.5 秒后放弃，通用图标；Explorer 不卡 | ☐ |
| 18 | 换回真 helper | 正常 | ☐ |
| 19 | 复制一个 500 MB 文件改名成 `.apk` | 快速回退（几秒内），**不冻结目录** | ☐ |
| 20 | 打开一个含 50 个 APK 的目录 | 逐个出图，界面可操作（不整体卡住） | ☐ |

### 3.1 造一个「卡住」的 helper

```powershell
# 在安装目录里（先把真的改名备份）
Copy-Item "$env:SystemRoot\System32\timeout.exe" .\app_icon_extractor.exe -Force
```

`timeout.exe` 不带参数运行会立刻退出，不一定卡住；更可靠的做法是用
`ping -t 127.0.0.1` 包一层。但**最省事**的做法是直接测超时逻辑的另一种形态：
把 helper 换成一个**不存在依赖**的程序（比如 `curl.exe`），它大概率立刻报错退出 ——
这验证的是「非 0 退出码 → 回退文件图标」。真正的超时只有真卡住才能验，
可选做。

> 如果你愿意花 2 分钟：写一个 `stall.bat` 内容 `ping -n 30 127.0.0.1 > nul`，
> 改名成 `app_icon_extractor.exe` 放进去。点开目录时应在 1.5 秒内回退，
> **而不是等 30 秒**。这条能直接证伪「超时没生效」。

## 5. 注册表核对（可选，但出错时很有用）

```powershell
# 1) 处理器指向哪里
reg query "HKCU\Software\Classes\CLSID\{9C4A7E52-3B7D-4E31-9A4C-6D2F8B1E5A70}\InprocServer32"

#    预期：Default 的值 = <安装目录>\appinfotool_thumbnail.dll
#          ThreadingModel = Apartment

# 2) 哪些扩展名挂上了
reg query "HKCU\Software\Classes\.apk\ShellEx\{e357fccd-a995-4576-b01f-ace3639130c9}"
reg query "HKCU\Software\Classes\.ipa\ShellEx\{e357fccd-a995-4576-b01f-ace3639130c9}"

#    预期：Default 的值 = {9C4A7E52-3B7D-4E31-9A4C-6D2F8B1E5A70}
```

**出问题时先跑这个**：注册表指向的路径与安装目录不一致，是「图标不出来」
最常见的原因，而界面已经能自动检测到并提示。

## 6. 出问题时怎么定位

按这个顺序，能把问题范围缩到一层：

| 现象 | 先查 | 说明 |
|---|---|---|
| 设置页状态就是错的 | 设置页 | 状态不对说明通道或文件缺失，还没到 Explorer 那层 |
| 状态「已启用」但没图标 | §5 注册表 | 键不在 / 路径不对 |
| 注册表对但没图标 | 手工跑自检（见下） | 分清是 DLL 的问题还是 Shell 的问题 |
| 自检 OK 但 Explorer 没图 | 清缩略图缓存 | `磁盘清理 → 缩略图`，或换个目录试 |
| 全部 APK 都出同一个图 | 立刻停下报告 | 这是**严重**问题：说明没按文件内容取图 |

### 手工跑自检

安装目录里的自检程序是构建产物，**不在安装包里**。要跑它，用 CI artifact 里的
`windows-release` 包（解压后 `runner/Release` 里应有
`appinfotool_thumbnail_selftest.exe`）；或者从构建目录直接跑：

```
cd build\windows\x64\runner\Release
.\appinfotool_thumbnail_selftest.exe D:\thumb-test\a.apk D:\thumb-test\b.apk
```

预期输出两行 `OK ... hash=XXXXXXXX`，且**两个 hash 不同**。

## 附录：CI 自检目前是「软门禁」

`Self-test the thumbnail provider` 这一步现在是 `continue-on-error: true`。
**原因不是它通过了，而是我还不知道它为什么没通过。**

### 已知

| 结论 | 证据 |
|---|---|
| selftest **能编译、能链接** | `Build Windows` 步骤成功 |
| 脚本**确实启动了** | `::notice::thumbnail self-test script started` 出现过 |
| 不是 YAML/解析层问题 | 同上（解析错误不会执行到 notice） |
| 不是 PowerShell 的错误策略 | 改用 cmd 后行为一样 |
| 拿不到 job 日志 | `GET .../actions/jobs/{id}/logs` → 403（需要 admin） |
| check-run 也没有更多信息 | `output.summary` / `output.text` 均为空，只有 2 条注解 |

命令行（`cmd` 与 `pwsh` 两版）都只留下 GitHub 自动加的那句
`Process completed with exit code 1`，我写的 `::error::` 一条都没出现。
这说明脚本在第一个 `echo ::error::` 之前就退出了 —— 但它明明打印过 notice。

### 所以请先做这一件事

**在哪下**：这个文件在 **Actions 的运行记录**里，**不在 Release 页面**。

```
https://github.com/wongbaye26-dot/appinfotools/actions/runs/39217745811
```

打开后滚到页面**最底部**的 **Artifacts** 区块，点 `windows-thumbnail-selftest`
（3.19 MB）。注意两点：

- **需要登录 GitHub** —— artifact 不像 Release 资产那样匿名可取；
- **默认 90 天后被清理** —— 过期的就重新跑一次 CI 或用 Release 里的安装包
  里的同名文件（`appinfotool_thumbnail.dll` + `app_icon_extractor.exe`），
  只缺 selftest 本体。

解压后是**平铺的三个文件**（不是文件夹），三个必须在同一目录 ——
selftest 按**自己所在目录**找另外两个：

```
appinfotool_thumbnail_selftest.exe
appinfotool_thumbnail.dll
app_icon_extractor.exe
```

把仓库里的两个夹具也放进去，然后：

```cmd
cd <解压目录>
appinfotool_thumbnail_selftest.exe ..\icon-png.apk
```

把**完整输出**贴回来。三种可能：

| 输出 | 含义 | 下一步 |
|---|---|---|
| `OK ... 72x72 hash=...` | DLL 层正常，CI 失败在脚本编排 | 我改 CI，功能本身没问题 |
| `FAIL ... cannot load ...` | DLL 依赖缺失或路径不对 | 我修加载逻辑 |
| `FAIL ... hr=0x...` | 调用链某处失败 | 按 hr 码定位 |
| 程序闪退 / 无输出 | 崩溃 | 严重，优先修 |

### 为什么这一步不能省

规格第十章要求「Windows 实测记录」，而 CI 只能证明「编译通过」。
自检程序的价值正是把「DLL 能不能出图」从人眼里拆出来 ——
但如果连它自己的输出都拿不到，这一层就等于没验。

**在它跑通之前，主验收清单（§2–§4）的结论都要打折扣**：
图标不出来时无法判断是 DLL 的问题还是注册的问题。
