> 版本：`2.5.0`（Windows 部分）

## 0. 一句话

Windows 文件资源管理器里，`.apk` / `.ipa` 显示各自应用的真实图标。
**不需要任何代码签名证书**；不需要打开主应用；不执行包内任何代码。

范围**只包含 Windows**。macOS 的 Quick Look 扩展不在本版（见可行性评估 §4.3：
分发需要付费开发者账号）。

## 1. 架构：为什么是「DLL + 独立 exe」

```
explorer.exe
  └─ appinfotool_thumbnail.dll        (in-proc COM，只做转发)
       └─ CreateProcessW ──► app_icon_extractor.exe   (AOT，纯 Dart)
                                 └─ 读 ZIP → 取图标字节 → 写临时文件
       ◄── WIC 解码临时文件 ──► HBITMAP ──► Shell
```

三条硬约束决定了这个形状：

| 约束 | 后果 |
|---|---|
| Explorer 用 **in-proc** 加载缩略图处理器 | 解析崩溃会**带崩整个桌面**，所以解析必须出进程 |
| Dart 运行时无法嵌入已有消息循环的宿主进程 | DLL 里跑不了 Flutter 引擎 |
| `dart:ui`（`Canvas` / `PictureRecorder`）**无法 AOT** | 主应用的自适应图标渲染器**不能**复用（实测 `dart compile exe` 失败） |

因此：

- **DLL 只做四件事**：拿路径、起进程、等超时、用 WIC 解码；
- **所有解析在独立进程**，超时直接 `TerminateProcess`；
- 解析代码与主应用**共用** `apk_parser` / `ipa_parser` / `archive_safety`，不复制一份。

## 3. 关键设计决定（都带理由，便于日后推翻时知道在推翻什么）

### 3.1 输出「原始字节 + 格式」，不转 PNG

首版只发 PNG，在 32 个真实样本上覆盖率 **81%（26/32）**。
失败原因里 4 个是 **WebP** —— Android Studio 从 AGP 3.0 起把 launcher 图标生成为
`.webp`。改成「发原始字节 + 格式」，由 Windows 的 WIC 解码后升到 **97%（31/32）**。

纯 Dart 实现 VP8 解码是另一个工程，而系统本来就有解码器 —— 让系统解是正确选择。
唯一的代价是：装了 WebP 扩展的系统才能解 WebP。Windows 11 内置；
Windows 10 1809+ 通过 Store 的「WebP 图像扩展」提供（多数机器已有）。
**没有时 WIC 返回 `WINCODEC_ERR_COMPONENTNOTFOUND`，我们回退文件图标** —— 不崩、不猜。

### 3.2 像素上限在 helper 里判，不在 Explorer 里判

`maxIconPixels = 4096`。读 PNG 的 IHDR / WebP 的 VP8 头 / JPEG 的 SOF 段即可，
**不解码**。让一个 20000×20000 的图标进到 Explorer，解码要 1.6 GB 内存 —— 那是
用户为「浏览一个文件夹」付出的代价。

### 3.3 不放大

请求 256 px 而图标只有 48 px 时，返回 48 px 的图（Shell 自己会排）。
放大只会得到糊掉的方块，规格 4.4 明确禁止。

### 3.4 自适应图标：明确不支持，不降级

APK 只有 `<adaptive-icon>` XML 时返回 `android.adaptive_icon_unsupported`，
**不**退而取前景层或背景层 —— 那会显示一个缺了一半的图标，比没有更糟。

要补这一块，需要纯 Dart 的 SVG/Drawable 光栅化（约 600–900 行：
path fill、linear/radial gradient、clip、alpha 合成），是独立工作项。

### 3.5 超时 1.5 s，超时即杀

真实样本实测 55–630 ms（最慢的是 343 MB 的抖音，且它本身拿不到图标）。
1.5 s 是「正常包必定跑完、异常包不拖住 Explorer」的折中。

### 3.6 注册只写 `HKCU`

与现有 `FileAssociationChannel` 同一条路：免管理员，不碰 `UserChoice`，
不碰其它应用的 `ShellEx`。卸载只删我们自己的两个键。

**inno_bundle 没有 Registry 段**（只支持额外 `files`），所以注册由应用自己在运行时做。

## 4. 现有能力的实际覆盖率（实测，非估计）

样本：本机 31 个 APK + 1 个 IPA（含加固包、大包、无图标包）。

| 结果 | 数量 | 说明 |
|---|---:|---|
| 成功 | **31** | 其中 IPA 走 `Assets.car`，1024×1024 |
| 失败 | 1 | 抖音 343 MB：`android.no_icon_declared`（加固/资源表问题） |

失败原因的分布（首版 128 MiB 上限时）：

| reason | 数量 | 现在的状态 |
|---|---:|---|
| `android.webp_unsupported` | 4 | **已修**（改为发原始字节 + 格式） |
| `input.file_too_large` | 1 | **已修**（上限提到 512 MiB，实测 0.63 s） |
| `android.no_icon_declared` | 1 | 内容问题，如实报告 |

**注意**：加固包会给出**诱饵图标**。`sun1.apk` / `sun2.apk` 的 ZIP 条目名被改写
（`res/values/plurals.xml/ic_launcher.png`），能取到一张 48×48 的假图。
我们按「拿到什么给什么」处理 —— 判定「这是诱饵」需要另一套证据，不属于缩略图职责。

## 5. 构建

```bash
# 1) 主程序（含 COM DLL）
flutter build windows --release
#   → build/windows/x64/runner/Release/
#       appinfotool_thumbnail.dll   （由 windows/thumbnail/CMakeLists.txt 产出）

# 2) 图标提取器（必须放在同一个目录，DLL 按同目录找它）
dart pub get --directory packages/app_icon_extractor
dart compile exe packages/app_icon_extractor/bin/app_icon_extractor.dart \
  -o build/windows/x64/runner/Release/app_icon_extractor.exe

# 3) 安装包（inno_bundle 会打包整个 Release 目录）
dart run inno_bundle:build --release
```

CI 已在 Windows job 里加好第 2 步（`.github/workflows/build.yml`），
并在打包前 `test -f` 校验两个产物都在 —— 缺 helper 的表现是
「缩略图永远不出来」，没有断言的话根本发现不了。

## 6. 验证清单（**必须在真 Windows 上做**）

> 这一节不能由 CI 代替。CI 是虚拟机，没有交互式桌面，
> 无法目视 Explorer。规格第十章明确不接受「CI 编译成功」作为交付证据。

### 6.1 注册与状态

- [ ] 应用启动后，设置页「系统文件图标」显示 `usable = true`
- [ ] 手工删掉 `app_icon_extractor.exe` 后重启应用 → 状态变 `usable = false`，
      且**原因明确**（`helperPresent = false`），不是一句「未启用」
- [ ] 注册后 `reg query "HKCU\Software\Classes\CLSID\{9C4A7E52-3B7D-4E31-9A4C-6D2F8B1E5A70}\InprocServer32"` 指向安装目录
- [ ] `reg query "HKCU\Software\Classes\.apk\ShellEx"` 含 `{e357fccd-...}`

### 6.2 缩略图（核心）

- [ ] 两个内容不同的 `.apk` → **两个不同的图标**
- [ ] 两个内容不同的 `.ipa` → **两个不同的图标**
- [ ] 图标与主应用里显示的一致（这就是 `test/icon_extractor_consistency_test.dart` 守的那条）
- [ ] 大图标视图、中图标视图都有图
- [ ] 小图标 / 列表 / 详细信息视图：**允许**是统一的文件类型图标（本版不做 `IExtractIcon`）
- [ ] 关掉「显示缩略图而不是图标」（文件夹选项 → 查看）后，行为跟随系统设置
- [ ] 重启 Explorer 后仍然可用
- [ ] 复制一个新 `.apk` 进目录，缩略图自动出现（无需重启）

### 6.3 失败与安全

- [ ] 损坏的 `.apk`（随便写几个字节改名）→ 文件图标，**Explorer 不崩**
- [ ] 无图标的 `.apk`（`test/fixtures/apk/signed-v2-v3.apk`）→ 文件图标
- [ ] 自适应图标的 `.apk`（`icon-adaptive.apk`）→ 文件图标（本版明确不支持）
- [ ] 把 `app_icon_extractor.exe` 换成 `cmd.exe` → 仍然不崩（应超时或非 0 退出）
- [ ] 一个 500 MB 的假 APK → 快速回退，不卡住目录
- [ ] 连续打开一个含 50 个 APK 的目录 → 界面不冻结（异步队列，逐个出图）

### 6.4 安装 / 升级 / 卸载

- [ ] 覆盖安装新版本 → 缩略图仍可用（注册指向的路径没变）
- [ ] 把安装目录**移动**后再打开应用 → 状态显示 `registered = false`
      且 `registeredPath` 指向旧路径（这是最容易漏的一种「假成功」）
- [ ] 卸载 → `CLSID` 与 `ShellEx` 两个键都被删掉，`.apk` 默认打开方式不变

## 7. 已知限制

| 限制 | 影响 | 出路 |
|---|---|---|
| 自适应图标不支持 | 只有 `<adaptive-icon>` 的 APK 显示文件图标 | 纯 Dart 光栅化，或 C++ 侧实现 |
| WebP 依赖系统解码器 | 无 WebP 扩展的 Win10 上，WebP 图标回退 | 随包分发 WebP 解码器，或只在 helper 里转码 |
| 加固包的诱饵图标 | 可能显示一张假图（48×48） | 需要独立的「加固判定」证据，不属缩略图职责 |
| 大包首次出图慢 | 343 MB 的包冷启动 ~0.6 s | 磁盘缓存（键 = 路径+大小+mtime+sha256 前 16 位）尚未实现 |
| 小图标视图不区分 | 列表视图是统一图标 | `IExtractIcon`，规格 2.3 允许不做 |
| ARM64 Windows | x64 DLL 在 ARM64 Explorer 里不加载 | 补一个 ARM64 构建 |
| **未在真机上目视验证** | 见下 | 需要一台真 Windows 11 |

### 编译状态：已通过 CI（2 轮）

第 1 轮（commit `25b1205`）失败在 COM 导出：

```
thumbnail_provider.cpp(614): error C2375: 'DllGetClassObject':
    redefinition; different linkage
thumbnail_provider.cpp(631): error C2375: 'DllCanUnloadNow':
    redefinition; different linkage
```

根因：`combaseapi.h` 已把这两个函数声明为 `WINOLEAPI`
（= `EXTERN_C HRESULT __stdcall`）。再叠 `__declspec(dllexport)` 定义同一个
函数，MSVC 认为 linkage 不同 —— dllexport 属性参与 linkage 判定。

修法：定义处保持 SDK 声明的原样，导出表交给 `appinfotool_thumbnail.def`
（`PRIVATE` 防止按修饰名导出）。

**这轮错误只出现在 614/631 行**，意味着前面 600 行都编译通过了 ——
`IThumbnailProvider` / `IInitializeWithItem` / `IInitializeWithStream` 的
接口与 IID、WIC 与 `ComPtr` 的用法、`propsys.h` 的引入都是对的。

第 2 轮（commit `1f41353`）**全部通过**：

| job | 结果 |
|---|---|
| Quality (format / analyze / test) | ✅ |
| External samples | ✅ |
| build-linux | ✅ |
| build-macos | ✅ |
| **build-windows** | ✅ |

Windows job 覆盖的环节（都过了）：

1. `flutter build windows --release` —— 编译 runner + **缩略图 DLL**（C++ 全部通过）；
2. AOT 编 `app_icon_extractor.exe`；
3. `test -f` 校验 helper 存在 + `ls` 列出 DLL —— **证明 DLL 真的落到了
   `runner/Release`**（这一条守的是 CMake 里 `CMAKE_INSTALL_PREFIX` 的设置顺序，
   放错位置会把 DLL 装到 `C:/Program Files/<project>` 而构建日志一片绿色）；
4. `inno_bundle` 生成安装包（打包整个 `runner/Release`，因此 DLL 与 helper 都在包里）。

### 仍未验证：真机行为

CI 是虚拟机、无交互式桌面，**不能目视 Explorer**。规格第十章明确不接受
「CI 编译成功」作为交付证据。以下必须在一台真 Windows 11 上做（清单见 §6）：

- 两个不同 APK / 两个不同 IPA 是否显示**各自**的图标；
- 损坏包、无图标包、自适应图标包是否正确回退且**不崩 Explorer**；
- 把 helper 换成别的程序后是否仍不崩；
- 重启 Explorer / 覆盖安装 / 移动安装目录 / 卸载后的行为。

**不能因为 CI 绿了就认为功能可用** —— 编译通过只证明代码是合法的 C++，
不证明缩略图会出现在资源管理器里。

## 8. 与规格的差异（有意为之）

| 规格 | 实现 | 为什么 |
|---|---|---|
| 2.1 首选 `IInitializeWithStream` | **首选 `IInitializeWithItem`**，Stream 作为备选 | Item 能拿真实路径，避免不必要的落盘；Stream 路径仍然实现了 |
| 4.1 接口返回「图标图像」 | 返回**原始字节 + 格式** | 转码让系统做，覆盖率从 81% → 97%（§3.1） |
| 7.2「使用现有 `archive_safety`」 | 纯 Dart 侧复用；C++/Swift 侧无法复用（它是 Dart 包） | 规格同句后半「保证一致的安全边界」才是可执行的那句 |
| 8.2 设置页 | 已实现（`SystemIconSection`），但只有状态 / 启停 / 刷新 / 诊断，没有「卸载组件」独立入口 | 停用即注销注册键，功能上等价；独立「卸载」按钮留给需要删文件的场景 |

## 9. 设置页

「设置 → 系统文件图标」（仅 Windows 渲染）。

### 9.1 显示什么

| 元素 | 说明 |
|---|---|
| 一句话 | 已启用时「资源管理器已按安装包内容显示真实应用图标」，否则「为每个 APK / IPA 显示它自己的应用图标」 |
| 状态行 | 「已启用 / 尚未启用 / 缺少缩略图处理器 / 缺少图标提取器」——**先报最根本的缺失** |
| 按钮 | 「启用 / 停用」，已启用时另有「刷新」 |
| 路径不一致警告 | 注册表写的路径 ≠ 当前 DLL 路径时单独一行，**两个路径都显示** |
| 逐扩展名 | `.apk` / `.ipa` 各自的注册状态（一个挂上一个没挂上时不能用「已启用」掩盖） |
| 诊断（折叠） | DLL 路径、helper 是否在场 |
| 已知限制 | 明确写出「只覆盖位图图标 / 小图标视图仍是统一图标」 |

### 9.2 三条显示规矩

1. **不可用必须说清是哪一步** —— 四种原因（DLL 缺失 / helper 缺失 / 未注册 / 路径不一致）
   的补救动作完全不同，压成一个 bool 用户没有可执行的下一步；
2. **不显示虚假成功** —— 只有 `usable` 为真才出现「已启用」；点「启用」后按**返回的实际状态**
   给提示，原生侧拒绝时不写「已启用」；
3. **不支持时不显示** —— 非 Windows 整块不渲染，而不是给一个永远打不开的开关。

### 9.3 为什么区块抽成独立 widget

`SystemIconSection` 接受注入的状态与回调，因此**能在 macOS / Linux 上真实渲染并驱动**。
留在 `setting_page.dart` 里时整块被 `Platform.isWindows` 门控，测试只能 `markTestSkipped` ——
那是「全跳过」，一个像素都没验证过。抽出来之后 16 条测试全部真实执行（含 9 条渲染断言）。

顺带 `setting_page.dart` 少了约 180 行。
