## 0. 本轮范围与约束

**目标**：让 Windows 资源管理器与 macOS Finder 直接显示 APK / IPA 的**真实应用图标**（缩略图），
无需打开主应用，且**不执行包内任何代码**。

**规格明确的两条硬约束**（贯穿全轮）：

1. **复用现有解析与图标提取能力**，禁止重写整套解析器或破坏现有功能。
2. **首期必须完成真实应用图标缩略图**；不得把所有 APK / IPA 共用一个通用图标当作已完成。
   Windows 小图标视图按文件显示各自图标的能力**先做技术验证**，再决定是否与首期一起交付。

**阶段划分**（规格第九 / 十章）：0 架构审计 → 1 最小 PoC →（**架构评审门禁**）→ 2 核心图标提取 →
3 系统集成 → 4 安全/性能/边界测试 → 5 发布验收。

## 2. 图标提取能力清单（规格第四章的输入）

### 2.1 结论先行：**两条链路的可复用性完全不同**

| 链路 | 关键实现 | 依赖 `dart:ui`（Flutter 引擎）？ | 能否在无引擎进程里跑 |
|---|---|---|---|
| **IPA 图标定位 + 取字节** | `packages/ipa_parser/lib/src/ipa_icon.dart` | **否**（纯 Dart） | ✅ **可以** |
| **IPA CgBI 解码** | `packages/ipa_parser/lib/src/cgbi_png.dart` | **否**（纯 Dart） | ✅ 可以 |
| **APK manifest / arsc / ZIP** | `packages/apk_parser/`（`pubspec.yaml` 里 **0 处** `flutter`） | **否** | ✅ 可以 |
| **APK 矢量/自适应图标栅格化** | `lib/apkparser/adaptive_icon_renderer.dart` | **是** —— `PictureRecorder` / `Canvas` / `Picture.toImage()`（`dart:ui`） | ❌ **不可以** |
| **PNG 编码（所有导出共用）** | `ui.Image.toByteData(format: ImageByteFormat.png)`，4 处调用点 | **是** | ❌ 不可以 |
| **IPA 图标解码成可显示图像** | `lib/utils/ios_icon_decoder.dart`（`import 'dart:ui' as ui`） | **是** | ❌ 不可以 |
| **矢量 drawable → SVG 文本** | `lib/utils/vector_to_svg.dart` | 自身不直接用 `dart:ui`，但 **import 了** `adaptive_icon_renderer.dart` | ⚠️ **需一次小解耦**（见 §2.4） |

**这张表就是规格 §5.3「架构决策门禁」的核心输入**：
「方案 A：复用现有 Dart 核心」对 **IPA 位图图标**成立，对 **APK 矢量/自适应图标**不成立 ——
后者要么把 Flutter 引擎塞进辅助进程，要么在原生侧重实现栅格化。

### 2.2 APK 图标链路（实测）

| 能力 | 位置 | 状态 |
|---|---|---|
| 二进制 Manifest 解析 | `packages/apk_parser/lib/src/manifest_parser.dart` | ✅ 纯 Dart |
| 图标声明与资源引用 | `ApkMeta.applicationIcon` / `iconPaths: Map<int,String>`（`models.dart:64`） | ✅ 纯 Dart |
| `resources.arsc` 资源表 | `packages/apk_parser/lib/src/arsc_parser.dart` + `arsc/` | ✅ 纯 Dart |
| 多密度选择 | `apk_info.dart:873-929`（按 dpi 排序选） | ✅ 纯 Dart |
| 自适应图标前景/背景合成 | `adaptive_icon_renderer.dart`（`_kAdaptiveForegroundScaleBitmap=1.60` / `Vector=1.28`） | ⚠️ **需 `dart:ui`** |
| 矢量 drawable 渲染 | 同上（`path_drawing` + `Canvas`） | ⚠️ **需 `dart:ui`** |
| 资源引用环检测 | `packages/apk_parser/lib/src/arsc/reference_graph.dart` | ✅ 纯 Dart |
| 候选优先级 | `adaptive_icon_renderer.dart` 内部 | ⚠️ 与渲染耦合 |
| 外部 `aapt2` 兜底 | `AdaptiveIconRenderer({required aaptPath, …})`；`macos/tools/aapt2` 随包分发 | ⚠️ 见 §4 的沙箱/签名问题 |

**关键约束**：`AdaptiveIconRenderer.render()` 返回的是 **`dart:ui` 的 `Image`**
（`adaptive_icon_renderer.dart:196-245`），不是字节。要拿到 PNG 必须再走
`toByteData(format: png)` —— 那一步同样在 `dart:ui` 里。

### 2.3 IPA 图标链路（实测）

| 能力 | 位置 | 状态 |
|---|---|---|
| `Payload/*.app/Info.plist` | `packages/ipa_parser/lib/src/ipa_info_plist.dart` | ✅ 纯 Dart |
| 图标声明解析（6 种来源） | `IpaIconResolver.resolve(archive, info)`（`ipa_icon.dart:191`） | ✅ 纯 Dart |
| 候选图标 + **原始字节** | `IosIconCandidate.bytes: Uint8List?`（`ipa_icon.dart:74`） | ✅ **纯 Dart，可直接复用** |
| 尺寸/格式元数据 | `IosIconCandidate.pixelWidth/Height` / `IosImageFormat`（png/jpeg/gif/webp/heic/unknown） | ✅ 纯 Dart |
| CgBI（"PNG crush"）识别与规范化 | `packages/ipa_parser/lib/src/cgbi_png.dart` | ✅ 纯 Dart |
| 未解析项 + 原因 | `IosUnresolvedIcon{declared, reason, archivePath}` | ✅ 纯 Dart |
| **`Assets.car` 提取** | **全仓 0 处实现**（`grep Assets.car` 在 `lib/` 与 `packages/*/lib/` 无命中） | ❌ **未实现** |
| 图标解码成可显示图像 | `lib/utils/ios_icon_decoder.dart`（`dart:ui`） | ⚠️ 需 `dart:ui` |

**`Assets.car` 的准确现状**：`IosIconSource.assetCatalogName` 能**识别**「图标由
`CFBundleIconName` 指向 `Assets.car`」，但提取不了 —— 会落到 `IosUnresolvedIcon` 并带原因；
界面上的说法是「图标位于 Assets.car，无法预览」（i18n `ios_info.icon_asset_catalog`）。
这与规格 §4.3 的预期一致（「首期先完成已有 PNG 路线，再对 `Assets.car` 做专项验证」）。

### 2.4 一处**小而关键**的解耦机会

`lib/utils/vector_to_svg.dart` 只从 `adaptive_icon_renderer.dart` 用到
**`AdaptiveIconSvgData`**（一个纯数据类：`backgroundColor` / `backgroundVector` /
`foregroundVector` / `foregroundScale`）。也就是说：

> 把 `AdaptiveIconSvgData` 从 `adaptive_icon_renderer.dart` 挪到一个**不 import `dart:ui`**
> 的文件里，`vector_to_svg.dart` 就能在无引擎进程里产出 **SVG 文本**。

这给 APK 矢量图标开了一条**不依赖 Flutter 引擎**的路：纯 Dart 产出 SVG → 原生侧栅格化。
但要注意 **Windows 没有内置 SVG 栅格化器**，macOS 的 `NSImage` 对 SVG 支持也有限 ——
所以这条路的可行性**必须进阶段 1 的 PoC 实测**，不能只看设计。

## 4. Windows 与 macOS 原生集成差距

### 4.1 Windows：**从零开始**

| 需要的东西 | 现状 |
|---|---|
| Shell 缩略图处理器（`IThumbnailProvider` + `IInitializeWithStream`） | **不存在**。`windows/` 只有标准 Flutter runner（`runner/*.cpp`、CMake） |
| COM 注册（CLSID / 64 位 / 按扩展名） | **不存在** |
| 安装器注册缩略图处理器 | **不存在**。安装器是 `inno_bundle`（Inno Setup），配置在 `pubspec.yaml:73+`，目前只做常规安装 |
| 缓存刷新（`SHChangeNotify` 等） | **不存在** |
| `IExtractIconW`（小图标视图，规格 §2.3） | **不存在**（且规格要求先做技术验证） |

**阶段 1 要在 Windows 上新建**：一个 ATL/Win32 的 DLL 工程（缩略图处理器）、
COM 注册脚本、以及 `inno_bundle` 的自定义安装/卸载脚本。
**注意位数**：Flutter Windows 产物是 x64；缩略图处理器必须与 Explorer 位数一致（x64），
且安装器需要能注册它。

### 4.2 macOS：**缺口比 Windows 更微妙，且有签名硬风险**

| 需要的东西 | 现状 |
|---|---|
| Quick Look Thumbnail Extension（`.appex` + `QLThumbnailProvider`） | **不存在**。`grep -c "appex"` 在 `macos/Runner.xcodeproj/project.pbxproj` 为 **0** |
| `QLSupportedContentTypes` 声明 | **不存在** |
| UTI 声明（`UTExportedTypeDeclarations`） | **不存在**。`macos/Runner/Info.plist` **没有** `CFBundleDocumentTypes`，pbxproj 里 `INFOPLIST_KEY_*` 也只有 `LSApplicationCategoryType` |
| 宿主 App 的文件类型关联 | **只有「打开系统设置页」**：`lib/utils/file_association.dart` 打开
`x-apple.systempreferences:…`；`macos/Runner/FileAssociationPlugin.swift` 只有 26 行，
**仅处理 `getInitialFilePath`**（读 UserDefaults），不做任何注册 |
| 扩展的构建/签名/嵌入流程 | **不存在**（CI 里 `grep -c "appex\|extension"` 为 **0**） |

#### ⚠️ 最大的架构风险：**当前是 ad-hoc 签名，没有 Developer ID**

```
macos/Runner.xcodeproj/project.pbxproj
  CODE_SIGN_IDENTITY = "-"          ← ad-hoc
  CODE_SIGN_IDENTITY[sdk=macosx*] = "-"
  CODE_SIGN_STYLE = Automatic / Manual（混用）
  （全文件无 DEVELOPMENT_TEAM）
```

macOS 的 **app extension 是独立进程**，系统加载它要**单独验证其签名**。用 ad-hoc 签名的
`.appex` 能否被 `quicklookd` 正常加载，**必须在阶段 1 的 PoC 里用「正式签名构建」实测** ——
这正是规格 §3.3 强调的「不能只在 Xcode 调试模式下验证成功就认定发布包可用」。
如果 ad-hoc 不行，本项目就要面对一个**产品决策**：是否引入 Developer ID 与公证
（那会改变现在的分发方式 —— 现在是「DMG + 让用户 `xattr -dr com.apple.quarantine`」）。

#### ⚠️ 第二个风险：**沙箱语义**

本项目**刻意不开沙箱**（`Release.entitlements` 里没有 `com.apple.security.app-sandbox`，
理由是重命名要在用户选中文件所在目录里新建文件）。但 **app extension 通常被系统要求沙箱化**，
且扩展有**自己独立的沙箱上下文**，不会继承宿主「非沙箱」这一状态。这意味着：

> 扩展里能读什么、能不能调用随包的 `aapt2` / 辅助进程，**不能从宿主 App 现在的行为推断**，
> 必须单独实测（规格 §3.3 已点名这一条）。

### 4.3 随包分发的二进制（两条链路都会碰到）

`macos/tools/{aapt2, adb}` 各约 10 / 14 MB，通过 pbxproj 的 CopyFiles 阶段带
`CodeSignOnCopy` 嵌入 App。**扩展若要调用它们**，需要：签名有效、路径可达、
且不受扩展沙箱阻挡 —— 这三条都**未验证**。

## 5. 三平台发布流程现状（阶段 5 的输入）

`.github/workflows/build.yml`：

| 步骤 | 现状 |
|---|---|
| Windows | `flutter build windows --release` → `dart run inno_bundle:build --release` → 产物 `AppInfoTool-<v>-Windows-x86_64-Setup.exe` |
| macOS | `flutter build macos --release` → `create-dmg` → `hdiutil attach` 后 `codesign --verify --strict` 校验 → 上传 DMG。**没有显式 codesign 步骤**（ad-hoc 由 Flutter 完成） |
| Linux | `flutter build linux --release` → AppImage |
| 质量门禁 | `quality` job：format / `flutter analyze` / 根测试 / 逐包 `dart analyze` + `dart test` / `flutter build bundle`；在 **main 上也跑** |
| 发布 | `create-release`（tag）、`publish-scoop` / `publish-homebrew*`（仅在 `huanfeng/ApkInfoTool` 上跑，fork 上被 `if` 挡掉） |

**对 V2.5.0 的影响**：Windows 的缩略图处理器需要**新的构建产物**（DLL）并纳入
`inno_bundle` 的安装脚本；macOS 需要**新的 target**并纳入签名与 DMG。
两者都要求改 CI —— 而 CI 改动**无法在本机验证**（本机构建不了任何平台产物，
`flutter build macos` 在 SPM 那步被沙箱拒且**退出码是 0**）。

### 6.2 架构决策门禁要回答的问题（规格 §5.3）

必须先给出实测答案，而不是设计推断：

| # | 问题 | 为什么必须实测 |
|---|---|---|
| Q1 | 无 Flutter 引擎的进程能否复用现有提取能力？ | §2.1 的表显示：**IPA 位图可以，APK 矢量不行** —— 需要把「不行的那部分」量化 |

| Q5 | Windows：缩略图处理器用**独立进程**（背引擎）还是**原生重实现**栅格化？ | 两者维护成本差一个量级 |

### 6.3 验收条件（Windows）

- [ ] 一个最小 `IThumbnailProvider` 实现，能注册、能被 Explorer 调用。
- [ ] **对 1 个真实 APK 和 1 个真实 IPA 返回真实应用图标缩略图**（不是通用图标）。
- [ ] 失败路径：损坏文件 / 无图标 → 安全回退，**不使 Explorer 崩溃**。
- [ ] 记录注册方式、位数、以及「启用/禁用系统缩略图设置」时的行为。

### 6.4 验收条件（macOS）

- [ ] Quick Look Thumbnail Extension 能构建、能被系统发现。
- [ ] 为 APK / IPA 声明稳定的 UTI 与 `QLSupportedContentTypes`。
- [ ] **在正式签名构建（不是 Xcode 调试）下验证扩展可用**。
- [ ] 明确记录：签名方式、沙箱配置、以及**是否必须引入 Developer ID**。

### 6.5 交付物

- [ ] 两个平台的 PoC（可运行、可复现的步骤记录）。
- [ ] 运行环境与签名要求（含 §6.2 的 Q3/Q4 实测结论）。
- [ ] **复用 Dart 解析器的技术验证结果**（逐项对应 §3 的可复用接口清单）。
- [ ] 缓存、时延与安全限制的初步评估（含实测数字，不给未实测的毫秒承诺）。

**阶段 1 完成后先做架构评审，再决定进入阶段 2。**（规格 §9 原文）
