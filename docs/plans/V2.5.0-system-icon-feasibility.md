# V2.5.0「文件管理器显示真实应用图标」可行性评估

> 评估日期：2026-10-19
> 评估对象：`V2.5.0` 规格（Windows / macOS 文件管理器缩略图集成）
> 代码基线：`e8abc7b`（tag `v2.4.16`）+ 本分支三项修复（未提交）
> 性质：**只读评估**。本文档不修改任何生产代码。
> 方法：读工程配置 + 三个决定性实验（结果见 §3，可复现）

---

## 0. 结论

**功能可以实现，技术路线也清晰；但按这份规格的完整范围与验收方式，在当前条件下
「一次做完」不成立 —— 有两个硬阻断，不在代码里。**

一句话：**Windows 侧可以按计划推进，且不需要任何证书；macOS 侧分两档 ——
本机自用可以用免费证书，分发给用户必须付费账号；而「自适应图标」这一块，
现有 Dart 渲染器不能复用，必须新写一套光栅化。**

| 部分 | 判断 | 依据 |
|---|---|---|
| Windows 缩略图（PNG 图标路线） | **可做**，约 3–4 周 | COM DLL + 现有解析器的 AOT 化（§3.2 实测 55–73 ms/包） |
| Windows 自适应图标（XML 合成） | **要新写**，约 8–12 天 | 现有渲染器 14 个方法全依赖 `Canvas`，AOT 编译直接失败（§3.1） |
| macOS Quick Look 扩展 | **分发被阻断；本机自用待实测** | 本机 **0 个** codesigning 身份；项目 ad-hoc 签名；extension 强制沙箱（§3.3、§4.3） |
| macOS 真机验收 | **当前无法执行** | 本机构建不了 macOS 产物；CI 是虚拟机，不能目视 Finder（§3.4） |
| 小图标视图（`IExtractIcon`） | **建议不做** | 规格已允许保留统一图标；收益低、风险高（§6.3） |

**综合：如果把 2.5.0 的范围收到「Windows 缩略图 + APK/IPA 的 PNG 图标路线」，
一个人 5–7 周可以交付并验收，账号成本为零。**完整规格（含 macOS 分发 +
自适应图标）需要 **10–13 周**，外加 $99/年的开发者账号（仅 macOS 分发需要）。

### 1.2 规格低估或未料到的部分

| 规格表述 | 实际情况 |
|---|---|
| 「复用现有 Dart 核心」把图标提取包成「无界面 Dart 辅助程序」 | **APK 的自适应图标不能这么做** —— 渲染器依赖 `dart:ui` 的 `Canvas`/`PictureRecorder`/`toImage`，`dart compile exe` 直接编译失败（§3.1） |

## 2. 规格本身自洽、但需要明确取舍的三处

1. **1.2 把缩略图与类型图标分开** —— 这是对的，也是本项目一贯的口径（能力 vs 缺陷分开）。
   建议在实现时把「缩略图缺失」与「类型图标回退」在设置页里分别显示，而不是一个总开关。
2. **5.3 要求先 PoC 再定架构** —— 这条应当照办。本文档 §3 已经替它回答了最关键的一半
   （Dart 核心能否复用），剩下的一半是平台侧（§5）。
3. **6.2「不得在没有实测的情况下承诺固定毫秒数」** —— 本文档 §3.2 给了实测数字，
   但那是在**本机、单包、冷启动**下的；批量场景（一次目录 50 个文件）没有测，见 §6.2。

## 3. 三个决定性实验（本轮实测）

### 3.1 `dart:ui` 无法脱离 Flutter 引擎 —— 自适应图标渲染器不可复用

```
$ dart compile exe bin/main.dart        # 内容：PictureRecorder + Canvas + Paint
bin/main.dart:5:55: Error: Method not found: 'Paint'.
Error: AOT compilation failed
COMPILE_EXE=254
```

`dart:ui` 在 Dart SDK 里只有少量 shim（`Rect` 之类），`Canvas` / `Paint` / `PictureRecorder`
由 Flutter 引擎提供。因此：

- `lib/apkparser/adaptive_icon_renderer.dart`（2,261 行）**14 个 draw 方法全部**接
  `Canvas` 参数，无法在纯 Dart 进程里跑；
- 它导出的 `vector_to_svg.dart`（559 行）**是纯 Dart**（0 处 `dart:ui`），
  说明矢量**解析**已经完成，缺的只有「SVG → 像素」。

**这条决定了：**
- IPA 图标（PNG 路线）→ 纯 Dart 可复用 ✅
- APK 的位图图标（`res/mipmap-*/ic_launcher.png`）→ 纯 Dart 可复用 ✅
- APK 的**自适应图标**（`<adaptive-icon>` XML）→ **必须新写光栅化**，约 600–900 行
  （path fill、linear/radial gradient、clip、alpha 合成），或改走方案 B（C++ 侧实现）

### 3.2 纯 Dart AOT helper 可行，且性能达标

工程：`/tmp/iconpoc`（临时验证用，未入库），依赖本地 `apk_parser` / `ipa_parser` +
同一个 `archive` git 依赖。**四个包零 Flutter 依赖**，因此可直接 AOT。

```
$ dart compile exe bin/main.dart -o iconpoc
COMPILE=0        # 6.4 MB 单文件

$ ./iconpoc sun_signed.ipa          # 40.5 MB 真实 IPA，连进程启动在内
ipa iconBytes=295244 73ms
ipa iconBytes=295244 55ms
ipa iconBytes=295244 56ms
```

- **端到端 55–73 ms**（含进程启动、ZIP 目录、Info.plist、图标定位与解压）；
- 取到 295,244 字节的原始图标；
- 说明 `IpaIconResolver` 只读必要条目，没有全量解压（40 MB 包 55 ms）。

APK 侧未取得有效数字：仓库夹具的 manifest 都没有 `applicationIcon` 引用（探测返回 -3
= 无图标声明），本机也没有真实 APK 样本。**这一项必须在阶段 1 补测**，
因为 APK 路径需要解析整个 `resources.arsc`（真实包 1–8 MB），耗时可能比 IPA 高一个量级。

### 3.3 macOS 侧被签名硬阻断

```
$ security find-identity -v -p codesigning
     0 valid identities found

$ grep CODE_SIGN macos/Runner/Configs/*.xcconfig   # 无输出
$ flutter build macos --release                    # CI 里就是这么打的，没有任何签名步骤
```

现状：**ad-hoc 签名 + 不开沙箱**（`Release.entitlements` 里刻意没有
`com.apple.security.app-sandbox`，理由写在文件注释里：改名需要目录写权限）。
`project.pbxproj` 里没有任何 `CODE_SIGN_IDENTITY` / `DEVELOPMENT_TEAM`，即沿用
Flutter macOS 模板的默认 ad-hoc 签名。

而 App Extension 的硬要求是：

1. `com.apple.security.app-sandbox = true`（extension target 必须沙箱）；
2. 有效代码签名，且与宿主同一 team（`pluginkit` 校验 team / application-identifier）；
3. 由 `pluginkit` 注册并加载。

**ad-hoc 签名缺少 team identifier，`.appex` 极可能被 `pluginkit` 拒绝注册**
（典型表现是扩展压根不出现在「系统设置 → 登录项与扩展」，且 `qlmanage -m` 里看不到）。
这一条**本轮无法实测**（本机没有任何签名身份），所以标为「高置信度推断，而非实测结论」；
但它不影响结论：即便 ad-hoc 侥幸能加载，也无法通过正规渠道分发给用户 ——
用户下载的 DMG 里带一个 ad-hoc 签名的 appex，系统同样会拒。

**要跨过这一关，需要 Apple Developer Program 账号（付费）签 Developer ID。**
这不是「调一下配置」能解决的。当前没有账号、也没有任何证书。

附带影响：宿主不沙箱、extension 沙箱是**允许**的（两个 target 各自 entitlements），
所以不需要为此给主应用开沙箱 —— 这一点不用担心。

### 3.4 验证环境：本机与 CI 都不能完成规格的验收

| 验收项 | 本机（macOS 27.2 / Xcode 27） | CI |
|---|---|---|
| 构建 Windows 产物 | ❌ 只能各自主机 | ✅ `windows-latest` 可编译 |
| 构建 macOS 产物 | ❌ 沙箱拒绝（历史已确认） | ✅ 可编译 |
| **目视 Explorer 缩略图** | ❌ 无 Windows | ❌ 虚拟机无交互桌面 |
| **目视 Finder 缩略图** | ⚠️ 理论可做，但需要可加载的 extension（无证书） | ❌ 同上 |
| 卸载/升级回归 | ❌ | ❌ |

**这是本评估里最容易被忽略、但最影响排期的一条**：规格第十章要求「Windows 实测记录 /
macOS 实测记录」，而当前**没有任何环境能产出这两份记录**。
必须提前安排一台真 Windows 11 与一台有证书的 Mac，否则阶段 1 之后无法验收。

## 4. 硬阻断与前置条件

### 4.1 必须先解决（阻塞阶段 1 验收）

| # | 前置条件 | 影响 | 谁能解决 |
|---|---|---|---|
| B1 | **macOS 侧**：至少一份可用于签名的身份（免费 Apple ID 的 Apple Development 证书即可本机自用；分发给用户则需 Developer ID） | 只影响 macOS；**Windows 不需要任何证书**（见 §4.3） | 用户 |
| B2 | 一台真实 Windows 11（x64） | Windows 侧目视验收 | 用户 |
| B3 | 一台有图形界面的 Mac（可与 B1 同机） | macOS 目视验收 | 用户 |

**B1 的准确边界见 §4.3**：它不是「必须买账号」，而是「必须有签名身份」。
本机自用可以用免费证书或 ad-hoc；只有**分发**才必须付费。
唯一确定无法绕行的是「不做扩展就想要每个文件各自的图标」—— 那需要扩展，
而扩展必须有签名。另一个方向「不做系统集成，只做拖放」则不属于本需求。

### 4.2 可以带风险推进（阶段 1 PoC 必须回答）

| # | 风险 | 为什么是风险 | 验证方式 |
|---|---|---|---|
| R1 | **Windows in-proc DLL 崩溃会带崩 Explorer** | 缩略图处理器跑在 `explorer.exe` 里，任何未捕获异常/无限等待都会让整个桌面卡死 | PoC 里注入畸形输入 + 强制超时 + `__try/__except`，在真机反复触发 |
| R2 | **in-proc DLL 里不能跑 Flutter 引擎** | FlutterEngine 需要 UI 线程/GPU/消息循环，且体积与启动开销都不合适。所以「复用 Dart 核心」只能是**外部 helper 进程 + IPC** | PoC 里实测「DLL → CreateProcess → 读 PNG", 并测 50 并发下的总耗时 |
| R3 | **macOS appex 起子进程后，子进程能否读目标文件** | 沙箱 extension（对用户选中文件的授权）**不自动继承**给子进程 | PoC 里在签名构建中实测；失败则降级为「extension 内纯 Swift 读 ZIP」 |
| R4 | **APK 自适应图标占比未知** | 如果绝大多数真实 APK 只提供 `<adaptive-icon>` XML，那「PNG 优先」的首期覆盖率会很低 | 拿 20–30 个真实 APK 统计：`applicationIcon` 指向 PNG 的比例 |
| R5 | **ARM64 Windows** | Explorer 是 ARM64，in-proc COM 必须同位数；x64 DLL 在 ARM64 Explorer 里不加载 | 明确列为已知限制，或补一个 ARM64 构建 |

### 4.3 没有开发者账号，可以吗？—— 分三种情况，答案不同

先把「签名」这件事拆成两个互不相干的问题：**能不能在自己机器上跑起来**，与
**能不能发给别人用**。这两件事的门槛差一个付费账号。

| 场景 | 需要什么 | 没有账号能行吗 |
|---|---|---|
| **Windows 缩略图（全部功能）** | 无。COM DLL 注册进 `HKCU\Software\Classes\CLSID`，不需要任何证书 | ✅ **完全不需要** |
| macOS 本机自用（自己编译、自己看效果） | ad-hoc（`codesign -s -`）或免费 Apple ID 的 Apple Development 证书 | ⚠️ **大概率可以，本轮未实测** |
| macOS 分发给别人（DMG 下载安装） | Developer ID Application 证书 + **notarization（公证）** | ❌ **不行**，$99/年 |

#### Windows 侧：零成本，这一点没有争议

- `IThumbnailProvider` 是普通 in-proc COM 组件，注册只写 `HKCU`（与现有
  `file_association_channel.cpp` 同一条路，免管理员）；
- 不需要 Authenticode 签名，Windows 不校验缩略图处理器的发布者；
- 唯一的既有现象是 **SmartScreen 对未签名安装包的「未知发布者」提示** ——
  这与现状完全一样（现在的安装包也没签），不是本次新增的负担。

**结论：2.5.0 的 Windows 部分可以零成本完整交付。**

#### macOS 本机自用：可行，但有三个代价

Xcode 的签名设置里有 `Sign to Run Locally`（就是 ad-hoc）。本轮的静态检查：

```
$ codesign -f -s - --entitlements ext.entitlements Thumb.appex
$ codesign -dv --entitlements - Thumb.appex
CodeDirectory v=20400 ... flags=0x2(adhoc)
Signature=adhoc
TeamIdentifier=not set          ← 关键：没有 team
```

- 结构层面完全成立：`CFBundlePackageType = XPC!`、
  `NSExtensionPointIdentifier = com.apple.quicklook.thumbnail`、
  `com.apple.security.app-sandbox = true`，`codesign` 全部接受；
- 以 `-Xlinker -e -Xlinker _NSExtensionMain` 链接的 Swift 二进制也能正常产出。

**但 `pluginkit` / `qlmanage` 的端到端验证在本环境跑不通**：

```
$ qlmanage -t -s 64 -o out demo.png       # 系统自带 PNG，与我的扩展无关
sandbox initialization failed: Operation not permitted
```

对照组（系统本来就认识的 PNG）也报同一句，说明是**当前执行沙箱**不允许
`qlmanage` 初始化它自己的沙箱，而不是扩展本身有问题。`pluginkit -m` 同样返回
`unauthorized discovery flag (PKDiscoverAll)`。

因此「ad-hoc 的 `.appex` 能否被 `pluginkit` 加载」这一条，本轮**只能给出
高置信度推断，不能给出实测结论**：

- 支持它的证据：Xcode 的 `Sign to Run Locally` 是官方签名选项，
  且 [Apple Developer Forums](https://developer.apple.com/forums/thread/694784)
  明确把 ad-hoc 描述为「可以给内部测试者试用」的方式；
- 反对它的证据：ad-hoc **没有 team identifier**，而扩展与宿主的
  application-identifier 绑定关系需要 team —— 新版本 macOS 对这条的校验在收紧。

**必须在一台有图形界面的 Mac 上补做这个实验才能定案**（约 1 小时）：
重新签名 → 双击打开宿主 app → `系统设置 → 通用 → 登录项与扩展` 里看扩展是否出现 →
放一个 `.apk` 到 Finder 看有没有图标。若 ad-hoc 不行，就换**免费 Apple ID 的
Apple Development 证书**（Personal Team，有 team ID，7 天有效，到期重签）。

三个代价，都在可接受范围但要提前说清：

1. **只有自己的机器能用** —— 签出来的东西别人装不了；
2. **有效期短** —— ad-hoc 每次重编译都要重新注册；免费证书 7 天到期；
3. **不能公证** —— 做不到「用户双击 DMG 就能装」。

#### macOS 分发：这一条没有绕行方案

Gatekeeper 要求从网络下载的 app 必须由 Developer ID 签名并公证（notarized），
否则用户看到「无法验证开发者」；而未公证的 **appex** 还有额外一层 ——
系统对扩展的加载校验比普通 app 更严。这不是配置问题，是分发链的规则。

**$99/年**（Apple Developer Program），个人与公司同价。

#### 所以怎么定范围

| 方案 | 内容 | 成本 | 能否交付给用户 |
|---|---|---|---|
| **建议：2.5.0 只做 Windows** | Windows 缩略图 + APK/IPA 的 PNG 路线 | **0** | ✅ 完整交付 |
| 2.5.0 加「macOS 自用实验版」 | macOS 代码合入，功能开关默认关闭，只在本机验证 | 0（需一台能签的 Mac） | ⚠️ 只对开发者本人可用 |
| 2.5.0 加「macOS 正式版」 | 含公证与分发 | ¥700/年 | ✅ 完整交付 |

如果目标读者是**你自己 + 少数同事**，第二行就够了：代码写出来，本机跑通，
README 如实写「macOS 侧需要自行签名」。
如果是**给所有下载用户**，第三行是唯一选择。

### 4.4 一个不需要账号但也不满足需求的替代方案（供参考）

macOS 的 `Info.plist` 里有 `CFBundleDocumentTypes` + `CFBundleTypeIconFile`，
可以让 `.apk` / `.ipa` 在 Finder 里显示**一个统一的**图标（就像现在的系统默认行为，
但换成我们自己的图）。这**不需要扩展、不需要签名、不需要账号**。

但它**不满足**本需求 —— 规格 1.2 明确写了「不得把所有 APK、IPA 共用一个绿色机器人
或苹果文件图标，当作本需求已完成」。列在这里只是为了说明边界：
**「统一图标」是零成本的，「每个文件各自的真实图标」才需要扩展。**

## 5. 架构建议（针对 §3.1 的结论）

规格的「方案 A / 方案 B」二分不够细。按`dart:ui` 的实测结果，实际有三条路：

| 路线 | 适用 | 代价 |
|---|---|---|
| **A1：纯 Dart AOT helper** | IPA 全部（PNG + `Assets.car`）、APK 的 PNG 图标 | 已验证可行（§3.2）；启动 55–73 ms |
| **A2：Dart AOT helper + 新写 SVG 光栅化** | 追加 APK 自适应图标 | +600–900 行纯 Dart + 视觉回归夹具 |
| **B：原生最小核心（C++/Swift）** | 所有场景，但每个平台各写一遍 | Windows 1,500–2,500 行 C++；macOS 800–1,200 行 Swift |

**建议：A1 先行，A2 作为阶段 2b，B 只在 R3 失败时对 macOS 局部启用。**

理由：
- A1 已被实测证明可行且够快，且**四个包零 Flutter 依赖**这个特性是现成的红利；
- 若选 B，就要在两个语言里各实现一遍 ZIP + AXML + ARSC + PNG，一致性维护成本极高
  （规格 5.2 自己要求「必须用同一组安装包测试原生提取结果与主应用结果的一致性」——
  这个一致性测试本身就会成为长期负担）；
- `Assets.car` 在 Swift 里几乎不可行（LZFSE + BSP 容器），但**多数 IPA 的 `.app`
  根目录仍有 `AppIcon60x60@2x.png`**，所以 macOS 可以只走 PNG 路线而覆盖率不崩。

统一接口按规格 4.1 的 `AppIconExtractor` 设计即可，但**返回类型必须平台中立**：

```
AppIconResult {
  bytes: Uint8List?          // PNG
  source: enum { plistPng, adaptiveVector, assetsCar, none }
  status: enum { success, fallback, unsupported, invalidInput, resourceLimit }
  pixelSize: (int, int)?
  reasonCode: String?        // 稳定 code，供日志与诊断
}
```

状态机与现有 `FieldStatus` / `CoverageStatus` 同一套命名习惯，避免再造一套词。

## 6. 分阶段可行性

### 6.1 阶段 0：架构审计 —— 已完成 80%

本轮已经产出：图标提取能力清单（§1.1）、复用边界（§3.1）、两平台缺口（§4）。
剩下 20% 是「真实样本的图标形态统计」（R4），需要样本，0.5 天。

### 6.2 阶段 1：PoC —— 分平台看

**Windows（可独立推进，3–5 天）**

1. `windows/thumbnail/` 新建 `add_library(... SHARED)` target（CMake 已具备条件，
   现有 `runner/CMakeLists.txt` 就是同一套模式）；
2. 实现 `IThumbnailProvider` + `IInitializeWithStream`，注册到
   `HKCU\Software\Classes\.apk\ShellEx\{e357fccd-…}`（**per-user 免管理员**，
   与现有 `file_association_channel.cpp` 写 HKCU 的做法一致，不需要改安装器）；
3. `CreateProcess` 调 Dart helper，超时 1.5 s 强制 `TerminateProcess`；
4. 真机：两个不同 APK + 两个不同 IPA，验证图标不同；畸形包验证不崩 Explorer。

**这里有一个规格没写但必须做的决定**：helper 是「每次请求起一个进程」还是「常驻 + IPC」。
按 §3.2 的 55–73 ms/包，50 个文件串行约 3.5 s —— Explorer 本身是异步队列，可接受；
但 APK 若需解析 8 MB 的 `resources.arsc`，可能到 200–400 ms/个，届时必须加磁盘缓存。
**建议先做「进程 + 磁盘缓存（键 = 路径+大小+mtime+sha256 前 16 位）」，不做常驻守护。**

**macOS（被 B1 阻断，暂不可验收）**

工程侧可以先写（新建 `.appex` target、`Info.plist` 的 `QLSupportedContentTypes`、
UTI 声明），但**只要没有证书就看不到任何效果** —— 连「扩展有没有被系统识别」都测不了。
建议：**代码可以先合入，功能开关默认关闭，设置页显示「当前构建未签名，系统集成不可用」**。

## 7. 对规格的四条修改建议

1. **把 2.5.0 拆成两个版本。**
   `2.5.0` = Windows 缩略图 + PNG 路线；`2.6.0` = 自适应图标 + macOS。
   理由：macOS 被 B1 卡住，若绑在一起发布，Windows 侧会被一个外部依赖拖住。
2. **1.2 的「首期必须完成真实应用图标缩略图」加一个限定词：首期先覆盖
   `Info.plist`/`manifest` 直接指向 PNG 的包。** 自适应图标明确写在 2.6.0，
   否则首期覆盖率可能只有一半（R4 未测前无法承诺）。
3. **4.3 的「首期应先完成已有 PNG 图标路线，再对 `Assets.car` 做专项验证」
   建议直接改为「`Assets.car` 不进 2.5.0」。** 现有实现出图率约 50%，
   而 PNG 路线在真实 IPA 里通常也在（`.app` 根目录），投入产出不划算。
4. **第十章加一条：「原生侧的安全边界是新实现，不是复用 `archive_safety`」。**
   规格 7.2 已经有这个意思，但「使用现有能力」这句话会让实现者以为可以少写一半。

## 8. 需要用户先决策的三件事

1. **macOS 的分发范围怎么定？** —— 只给你自己和少数同事用：ad-hoc 或免费证书即可，
   零成本，但 README 要写明「需自行签名」；要发给所有下载用户：必须 Developer ID
   （$99/年）+ 公证。**Windows 侧与这个决定无关**，可以先开工（§4.3）。
2. **是否有真实 Windows 机器用于验收？** —— 没有的话，Windows 侧也只能交到「CI 能编译」，
   而规格第十章明确不接受这种交付。
3. **自适应图标是否必须在 2.5.0？** —— 必须在，则工期 +2–3 周（新写光栅化）；
   可以推到 2.6.0，则 2.5.0 的覆盖率要如实标注「仅 PNG 图标的包」。

import 'dart:ui' as ui;

DART
