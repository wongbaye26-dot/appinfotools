## 1. P1-1 解压预算：从「只看声明值」到两道闸

### 1.1 问题回顾（审计实测）

把 100 MiB 全零条目的中央目录 `uncompressedSize` 改成 1024：

```
open = ok                                    ← ZipBudget.check 只看声明值，放行
readFile 返回 104,857,600 字节，耗时 40ms     ← 实际解压 100 MiB
RSS 增量 201 MiB
```

根因：`archive-3.6.1/lib/src/zip/zip_file.dart:163-167` 在 IO 平台走 native
zlib（`inflateBuffer`），**忽略声明尺寸**。

### 1.2 改法：两道闸

`packages/archive_safety/lib/src/zip_budget.dart` 新增 `readEntry()`：

| 闸 | 判据 | 行为 |
|---|---|---|
| 第一道 | `file.size > maxBytes`（声明值） | **不解压就拒绝** —— 诚实的大条目不必浪费内存 |
| 第二道 | `content.length > maxBytes`（真实产出） | 丢弃并拒绝，日志记「声明 X 实际 Y」 |

接到三个读取点：

| 读取点 | 影响 |
|---|---|
| `packages/apk_parser/lib/src/apk_reader.dart` `readFile` | 内存（DEX / arsc / manifest / so） |
| `lib/utils/zip_helper.dart` `readFileContent` | 内存（IPA 侧） |
| `lib/utils/zip_helper.dart` `extractFile` | **磁盘**（此前一个几 MB 的包可以写满磁盘） |

### 1.3 已知局限（必须如实记录，不许含糊）

**这一版挡不住峰值内存。**

试过的路径与为什么不行：

1. **`archive` 的 `Inflate.stream` + `inflateNext`** —— `Inflate` 不在
   `package:archive/archive.dart` 的导出面里（`src/zlib/inflate.dart`），
   用它是 `implementation_imports`（lint 禁止 + 版本一升就碎）。
2. **`ZipFile.rawContent` 拿压缩字节** —— 运行时实测 `file.rawContent` 返回的是
   **`ZipFile` 对象本身**，而 `ZipFile` 上**没有** `rawContent` 这个 getter
   （`NoSuchMethodError`）。压缩字节在私有字段里，公开 API 拿不到。
3. **按 `compressed * 1032` 估上界做前置拒绝** —— 实测纯零数据的压缩比在
   `archive` 的 deflate 下只有 **229:1**，而 V2.4.10 要放行的填充清单是
   **205:1**。任何基于「压缩比上界」的前置拒绝都会把 V2.4.10 刚修好的样本
   重新挡在门外。

因此当前保证的是：**超限数据不会被保留、不会被写盘，并留下可追溯的日志**。
真正的解法有两条，都超出「改一行」的范围：

- 换用支持「带上限流式解压」的 ZIP 库；
- 自己解析 local file header 拿到压缩数据偏移，用 `ZLibDecoder` 接一个
  超限即抛的 `Sink`（需绕过 `archive` 的 `ZipFile`）。

**验收口径**：审计报告 §P1-1 写的是「被拒绝**或**解压到上限即中止」。
本轮达成前者，后者仍未达成 —— 记为遗留项。

## 2. P1-2 加固证据结构化

### 2.1 问题回顾

中文界面上是「容器/解析异常可能影响覆盖完整性：21 elements declare a
non-standard attributeStart (largest 343 on `<application>`)…」——
中文前缀 + 英文正文。用户已两次点名。

### 2.2 改法：证据带 code + 参数

| 层 | 改动 |
|---|---|
| `AxmlLayoutAnomalies`（`binary_xml.dart`） | 新增 `notes()` → 4 条 `AnalysisNote`（attributeStart / attributeSize / namespace chunk / unknown chunk），带 `count` / `largest` / `element` / `standard` / `chunks` |
| `HardeningObservation`（`hardening.dart`） | 新增可选 `note`；新增 `asNote`（优先 note，否则包成通用 `android.container.anomaly`）。**8 个观察点全部补上 note** |
| `ApkMeta`（`models.dart`） | 新增 `manifestLayoutNotes`，与 `manifestLayoutAnomalies` 按下标一一对应 |
| `AndroidSecurityAudit.audit` | 参数 `containerAnomalies: List<String>` → `containerAnomalyNotes: List<AnalysisNote>`，原样并入 limitations（不再二次包装） |
| `AnalysisReport.limitationNoteText` | 新增 13 个 code 的分支 |

**13 条 code**：

```
android.container.missing_primary_dex
android.container.multiple_dex_files
android.container.dex_header_unreadable
android.container.dex_header_not_standard
android.container.unusual_native_library
android.container.executable_in_assets
android.container.decoy_entries
android.container.resource_table_missing
android.container.resource_table_too_small
android.container.structure_anomaly
android.manifest.attribute_start_nonstandard
android.manifest.attribute_size_nonstandard
android.manifest.namespace_chunk_nonstandard
android.manifest.unknown_chunk
```

（`structure_anomaly` 复用 `android_container_anomaly` 的模板 —— 正文就是那句
结构说明。）

### 2.3 实测

`49af6cnn-1018.apk`（100 个诱饵条目 + 6 个 DEX）：

```
android.container.multiple_dex_files
   有 6 个 DEX 分片：classes.dex、classes2.dex、…。单凭分片不足以说明加固 ——
   现代应用因 64K 方法数上限也会分片。
android.container.decoy_entries
   100 个条目把「一个文件」当作目录前缀（例如 AndroidManifest.xml/依NھنصvK…）。
   正常归档不会这样，它专门用来打断「按路径解包」的提取器。
```

**面板里已经没有英文尾巴。**
