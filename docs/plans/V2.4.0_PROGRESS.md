### 无法在本机执行的命令（必须写明原因）

| 命令 | 原因 |
|---|---|
| `flutter build macos --release` | `xcodebuild` 解析 SPM 依赖时报 `sandbox-exec: sandbox_apply: Operation not permitted`；当前进程上下文禁止创建 `deny default` 风格沙箱。**与项目配置无关**，关掉工具沙箱重试同样失败。macOS 产物只能由 CI 的 macOS runner 产出。 |
| 启动 macOS / Windows / Linux 应用做交互验证 | 本机无法产出 macOS 可执行文件；拖放、取消解析、导出报告等**交互路径未在本机验证**。 |
| `dart test`（包级） | 四个包都声明了 `test` 依赖，但 `packages/*/test/` 里**没有任何测试文件**（`packages/ipa_parser/test/` 是空目录）。CI 也只对包跑 `dart analyze`，不跑测试。 |

### 真实样本测试（需要 `APPINFOTOOL_SAMPLES`）

样本目录：`/Users/wangbaye/Projects/ipa`（12 个 `.ipa`，**0 个 `.apk`**）。

```
APPINFOTOOL_SAMPLES=/Users/wangbaye/Projects/ipa \
  flutter test test/real_samples_test.dart test/real_samples_ui_test.dart
```

结果：**4 项失败**。逐条归因如下 —— **其中 2 项是测试脚手架缺陷，2 项是环境缺样本，均不是产品缺陷**。

| # | 失败项 | 归因 | 证据 |
|---|---|---|---|
| 1 | `real_samples_test.dart` 真实 APK 样本 每个样本都能解析完成 | **环境**：样本目录里没有 `.apk` | 目录扩展名统计：12 个 `.ipa`，无 `.apk` |
| 2 | `real_samples_ui_test.dart` 真实 APK 的详情页 (setUpAll) | **环境**：同上，`_firstSample('.apk')` 返回 `null`，`sample!` 抛 `Null check operator used on a null value` | `test/real_samples_ui_test.dart:153` |
| 3 | 真实 IPA 的详情页 · 签名结论与原始输出都出现在界面上 | **测试脚手架**：视口高度不足 | 见下方探针 |
| 4 | 真实 IPA 的详情页 · 被截断的嵌套清单在界面上有说明 | **测试脚手架**：同上 | 见下方探针 |

**探针取证（临时测试，跑完已删除）**：`test/real_samples_ui_test.dart` 的 `_pumpInfoPage`
把测试视口固定成 `1200×8000`，注释说「让整列卡片都进入布局范围」。但
`DetailTabView` 在测试环境走 `_buildTestView`，那是一棵 **`ListView`** —— 它只构建
视口内的子项。实测：

| 视口高度 | 渲染文本长度 | 含 `codesign verification` | 含 `ios.nested.truncated` |
|---|---|---|---|
| 8000（现状） | 15,218 | **否** | **否** |
| 40000 | 18,919 | **是** | **是** |

即：**产品侧渲染是正确的**，是测试的固定视口不再够高（样本的嵌套 Framework 有 27 个，
被截断到 24 条，卡片变长）。同时确认数据侧正常：`codesign toolExecuted=true
status=SignatureStatus.verified`，`diagnostics` 里确有 `ios.nested.truncated`。

> **这是一个流程问题，不只是两条测试的问题**：CI **没有**设置 `APPINFOTOOL_SAMPLES`
> （`grep -c APPINFOTOOL_SAMPLES .github/workflows/build.yml` = 0），这 11 项真实样本
> 测试**在 CI 里永远跳过**，因此可以长期失效而无人察觉。

#### 缺陷 COV-1：维度名渲染成机器 ID，未本地化

- **表现**：Markdown 报告的「Dimension」列、UI 覆盖卡片的每行行首，直接显示
  `android.dex.strings` 这类稳定标识。中英文界面都是如此。
- **最小复现**：构造一个含 4 条 `CoverageEntry`（id 分别为 `android.manifest`、
  `android.dex.strings`、`android.arsc`、`ios.signature`）的
  `AnalysisCoverage`，调 `AnalysisReport.render(...)`，读「## 分析覆盖」一节。
- **预期输出**：维度列是**人能读懂**的名字（例如「DEX 字符串」），且随界面语言变化。
- **实际输出**（`flutter test` 实跑打印，原文照抄）：

  ```
  | Dimension | Status | Amount | Note |
  | --- | --- | --- | --- |
  | android.manifest | Covered | — |  |
  | android.dex.strings | Partially covered | 1024/2048 |  |
  | android.arsc | Not covered | — | 资源表缺失 |
  | ios.signature | Not applicable | — |  |
  ```

- **根因**：`CoverageEntry.id` 的文档注释写着「UI 用它映射到本地化文案」
  （`analysis_coverage.dart:37-41`），但**这个映射不存在** ——
  `assets/i18n/*.json` 的 `coverage` 段只有四态标签与表头，没有任何维度名。
  两处呈现都直接写 `entry.id`：`analysis_report.dart:498`（Markdown）、
  `info_page.dart:798`（UI）。JSON 里保留 `id` 是对的（机器读），
  但 UI 与 Markdown 不该把机器标识直接给用户看。
- **关联源文件**：`packages/analysis_model/lib/src/analysis_coverage.dart:37-41`、
  `lib/utils/analysis_report.dart:497-501`、`lib/pages/info_page.dart:794-801`、
  `assets/i18n/{en,zh-CN,zh-HK,zh-TW,ja,ko}.json` 的 `coverage` 段。

#### 缺陷 COV-2：汇总句用中文全角分号硬拼接

- **表现**：英文报告里出现 `1 of 3 dimensions fully covered；2 dimensions have gaps`
  —— 分隔符是中文全角「；」。
- **最小复现**：同上（coverage 有缺口时就会命中）。
- **预期输出**：分隔符随语言变化（英文用 `; `）。
- **实际输出**：见上（`covered；2 dimensions`）。
- **根因**：`analysis_report.dart:521` 把两句用**字面量**「；」拼起来：
  ```dart
  return '${t.coverage.summary(...)}；${t.coverage.gap_count(...)}';
  ```
  两句本身都走了 i18n，只有标点没走。
- **关联源文件**：`lib/utils/analysis_report.dart:521`。

#### 缺陷 COV-3：引擎产出的 `note` 是硬编码中文（**本阶段不修**）

- **表现**：英文/日文/韩文报告与界面里，「说明」列会出现中文，例如
  「资源表缺失或解析失败」「清单未解析，权限审计无法进行」
  「Info.plist 未解析，用途说明未读取」。
- **根因**：`CoverageEntry.note` 是自由文本，由审计引擎直接生成：
  `android_security_audit.dart:746,830`、`ios_privacy_audit.dart:729,751,785`。
  而 `analysis_model` 是**零依赖**包、`apk_parser` / `ipa_parser` 都不依赖 slang
  —— 引擎层根本没有 i18n 能力。
- **为什么不在本阶段修**：正确做法是给 `CoverageEntry` 增加结构化的
  `noteCode` + 参数，由呈现层本地化。那属于**改覆盖模型**，而任务书明确要求
  「不得直接重构覆盖模型」。因此本阶段只记录，留给后续阶段（与 §7 阶段 3.3
  「覆盖率维度扩充」合并处理）。
- **关联源文件**：`packages/apk_parser/lib/src/security/android_security_audit.dart:746,830`、
  `packages/ipa_parser/lib/src/security/ios_privacy_audit.dart:729,751,785`。

#### 本阶段的修复范围

| 缺陷 | 处置 |
|---|---|
| COV-1 | **修**：补 15 个维度名的六语言文案 + 单点映射函数，UI 与 Markdown 共用；未知 id 原样回退 |
| COV-2 | **修**：分隔符走 i18n |
| COV-3 | **记录不修**：需要改模型，超出「最小修复」与本阶段范围 |

### 12.2 任务 B8：解析器对畸形输入的契约（**先定契约，再改代码**）

**现状（阶段 1 实测）**：`ManifestParser.parse` 与 `ArscParser` 在空/垃圾字节上
抛 `IndexError`；应用侧靠 `apk_reader.dart:194` 与 `parse_task.dart:200` 兜住。

**契约决定**：**解析器不抛异常，失败记成数据。**

| 解析器 | 失败时的行为 |
|---|---|
| `ManifestParser.parse` | 返回**空 `ApkMeta`**，并置 `manifestParseFailure`（新增字段，`String?`）。调用方据此区分「清单里什么都没有」与「清单没读出来」 |

**验收条件**
1. 空输入、垃圾字节、截断输入都不抛异常。
2. `ApkMeta.manifestParseFailure` 在解析失败时非空、成功时为 `null`。
3. `ArscParser.parseFailure` 同上；`getAllResources()` 不因此抛异常。
4. `ApkReader.parse` 在 manifest 解析失败时**仍返回 `null`**（保持既有语义，`parse_task` 的
   `manifestParsed: false` 分支不变）。
5. 真实夹具（加固清单、标准清单、真实 arsc）的解析结果**逐字段不变**（回归）。

**仍然是静态材料，不做任何验证**（规范 5.5）。

| 新增 | 作用 |
|---|---|
| `der.dart` | 极简 DER 读取器：越界返回 `null`、拒绝不定长、不做递归 |
| `x509.dart` | 从证书 DER 里取**公开字段**：主体/签发者 CN、有效期、序列号 |
| `CmsContentExtractor.extractCertificates` | 定位 SignedData 的证书集合，逐张交给 X.509 解析 |
| `IosCodeResourcesSummary` | `CodeResources` 的**结构**：密封文件数 / 规则数 / 是否 v2 |
| `IosSignatureMaterials.codeResources` / `.certificateChain` | 挂载点 |

**渲染**：`DetailRenderer.iosSignature`（UI 与 Markdown 共用）新增两段；
JSON 的 `signatureSummary` 新增 `codeResources` 与 `certificates`。
两者都带一句「这些只是材料，不代表证书可信，也不代表签名有效」。

**交叉核对（用独立工具，不从本项目取期望值）**

| 项 | 独立工具的结果 | 本实现的结果 |
|---|---|---|
| `33ZB_signed_v3.ipa` 的 `CodeResources` | — | 密封 3688 个文件 / 15 条规则 / v2 |
| `月光_signed_v3.ipa` 的 `CodeResources` | — | 密封 3638 个文件 / 15 条规则 / v2 |
| 真实 Apple 描述文件的证书链（`openssl pkcs7 -print_certs`） | **3 张**：`Apple iPhone OS Provisioning Profile Signing` ← `Apple iPhone Certification Authority` ← `Apple Root CA` | **3 张，CN 与签发者完全一致** |
| 夹具描述文件的证书（`openssl x509`） | 1 张，`CN=Probe`，`notAfter=Oct 15 15:34:07 2026 GMT`，`serial=9D872EE17763407E` | 完全一致 |

**交叉核对抓到一个真 BUG**：`_readCertificates` 最初把 `extractCertificates`
喂给了 `extract()` 出来的**载荷**（描述文件 plist），而不是 **CMS 原文** ——
于是真实 Apple 描述文件（链上 3 张证书）恒定解出 0 张。
**这正是「期望值必须取自独立工具」的价值**：如果只测「不抛异常 / 返回一个对象」，
这个 bug 会一直躲在一个「0 张证书」的合法结论背后 —— 0 张证书本身是可能的
（detached 签名就没有证书），单看实现看不出对错。

另一个小坑：DER 的 INTEGER 在最高位为 1 时会**补一个 `0x00`**，因此原始字节
比数值多一位（`009D872EE17763407E` vs `9D872EE17763407E`）。已按**值**输出，
与 `openssl` 一致。

## 13. 接口改动方案

**现状**：`IosPrivacyAudit.audit` 已经接收嵌套 bundle 的**可执行文件**字节
（阶段 5b，`nestedExecutables`），但**用途说明只看主应用**的 `Info.plist`。
于是「某个 App Extension 声明了相册/相机用途，主应用没有」这种情况完全看不到 ——
而扩展常常正是处理照片与 OCR 的地方。

**关键发现（决定了改动量）**：`lib/ipaparser/ipa_analysis.dart` 的
`_readNestedBinaries` **已经**为每个嵌套 bundle 调用了
`IpaInfoPlistReader.read(archive, bundle)`（为了拿 `CFBundleExecutable`），
只是把结果丢掉了。因此不需要新增解析，只要把用途说明**带出来**。

**改动**

| 文件 | 改什么 |
|---|---|
| `lib/ipaparser/ipa_analysis.dart` | `IosNestedBinary` 加 `usageDescriptions`；在已有的 `info` 上顺手取 |
| `packages/ipa_parser/…/ios_privacy_audit.dart` | `IosNestedExecutableInput` 加 `usageDescriptions`；审计逐 bundle 产出 `IOS-USAGE-DESCRIPTION`，`location` 指向**那个 bundle 的** Info.plist |
| `lib/pages/info_page.dart` | 把 `usageDescriptions` 传进去 |
| 覆盖率 | `ios.usageDescriptions` 的覆盖量把嵌套 bundle 的用途说明算进去 |
