## 0. 一句话结论

**V2.4.11 记的「做不到有界解压」是错的。** 我当时读的是 **pub.dev 的
`archive 3.6.1`**，而本项目实际用的是 **git 依赖**（`ref cb3a07c`）——
后者有 `ZipFile.decompress(OutputStream)`，是**真正的流式**接口。
给它喂一个带上限的 `OutputStream`，超限时在写那一块时抛异常，zlib 就地停下。

实测（5 MiB 全零条目，上限 1 MiB）：在 `observed = 1,067,098` 处抛出，
**已产出 1,001,562 字节就中止**，从未物化 5 MiB。

> **⚠️ 上面这段只说对了一半，收尾轮已推翻（见 §10.1）。**
> `decompress(OutputStream)` 底下是 `ChunkedConversionSink.withCallback`，
> 它**先把解压结果全部攒起来**再交给回调 —— 所以第一版只挡住了「我们保留
> 多少」，没挡住「解压器分配多少」。实测 256 MiB 条目 / 1 MiB 上限时
> ΔRSS 72 MiB。现在改成自己喂输入 + 自定义 `Sink`，同一场景 ΔRSS 16 KiB，
> 并有测试（`bounded_read_memory_test.dart`）守着。

## 2. 三道闸与共享预算

`readEntryBounded(file, maxEntryBytes, ledger)`：

| 闸 | 判据 | 行为 |
|---|---|---|
| 1 | `file.size`（**声明**解压大小） | 超限 → **不解压就拒绝** |
| 2 | `file.rawContent.compressedSize`（**声明**压缩大小） | 超限 → 连原始数据都不读 |
| 3 | **解压过程中真实产出** | 逐块写，超限的那一块抛异常 → **就地中止** |

- 单条目上限：**256 MiB**（`maxSingleEntryUncompressed`，未变）。
- 单条目压缩上限：**512 MiB**（`maxSingleEntryCompressed`，新增）。
- 一次读取流程的**真实产出**总量：**1 GiB**（`maxSessionOutputBytes`，新增）。
- 一次流程的**压缩**总量：**2 GiB**（`maxTotalCompressed`，新增）。

**共享预算**：`BoundedReadLedger` 由 `ApkReader` / `ZipHelper` / `ZipGuard`
各自持有，一次 `open` 一个；嵌套归档共用同一个实例 —— 子归档**拿不到**完整
独立配额（`test/bounded_read_test.dart` 的「嵌套归档共享预算」用例钉住这条）。

**超限诊断**：`BoundedReadFailure{entry, stage, observedBytes, limitBytes}`，
`describe()` 输出 `classes.dex: stopped at inflate after 1067098 bytes
(limit 1048576)` —— 条目、阶段、实际字节三项齐全。

## 4. 技术限制与选型（任务书第 10 条）

**结论：现有归档库支持安全的有界流式输出，因此没有「解压后再检查」的伪装。**

关键事实（读的是**实际依赖**的源码，不是 pub.dev）：

| 事实 | 位置 |
|---|---|
| `ZipFile.decompress(OutputStream)` 把 zlib 输出逐块写进调用方的 `OutputStream` | `archive-cb3a07c/lib/src/codecs/zip/zip_file.dart:164` |
| `OutputStream` 是**导出的抽象类**（`length` / `clear` / `flush` / `writeByte` / `writeBytes` / `writeStream` / `subset`） | `lib/src/util/output_stream.dart:7`，导出见 `lib/archive.dart:53` |
| 压缩字节在 `ZipFile` 构造时已物化（`readBytes(compressedSize)`） | `zip_file.dart:105` |

**被否决的备选方案**：

1. **自解析 local file header + `ZLibDecoder` 接上限 `Sink`** —— 可行（已用探针
   验证：`header.localHeaderOffset` 公开、`dart:io` 的 `ZLibDecoder` 接
   `Sink` 能中止），但要自己处理 Zip64 / data descriptor，代码量远大于
   `decompress(OutputStream)`，**没有必要**。
2. **`Inflate.stream` + `inflateNext`** —— 该 API 在本 git 版本里也存在
   （`lib/src/codecs/zlib/inflate.dart`，已导出），但 `decompress` 已经封装好
   了分块循环，直接用更省事。
3. **提高压缩比阈值 / 只做后置长度检查** —— 前者被 V2.4.10 证伪（229:1 vs
   205:1 无法区分），后者就是 V2.4.11 的临时方案，**峰值内存仍不受限**，本轮
   明确不采用。

## 10. 收尾轮（V2.4.12 第二轮）：补验证、补边界、推翻一处错误结论

> 起点：`main` @ `28e5306`（= tag `v2.4.12` = `origin/main`），工作区干净。
> 本轮**不升版本、不打 tag、不提交**，只补证据与整改。

### 10.1 一句话结论

**§0 那条结论要收回一半。** `ZipFile.decompress(OutputStream)` 确实会「逐块
写出来」，但它底下用的是 `ChunkedConversionSink.withCallback` —— 那个 sink
**先把解压结果全部攒起来**，到 `close()` 才交给回调。所以第一版的「有界」
只挡住了**我们保留多少**，没挡住**解压器分配多少**：

| 条目（全零，CD 谎报 1024） | 上限 | 第一版 ΔRSS / 耗时 | 现在 ΔRSS / 耗时 |
|---|---|---:|---:|
| 64 MiB | 1 MiB | **24 MiB / 9 ms** | 1.2 MiB / 0 ms |
| 64 MiB | 8 MiB | 21 MiB / 8 ms | 4.9 MiB / 0 ms |
| 256 MiB | 1 MiB | **72 MiB / 29 ms** | 16 KiB / 0 ms |
| 256 MiB | 8 MiB | 0.6 MiB / 31 ms | 2.3 MiB / 0 ms |

内存随**条目大小**涨，不随上限涨 —— 这就是「事后长度检查」的另一种伪装。
整改办法：自己按 1 KiB 喂输入给 `dart:io` 的 `ZLibCodec(raw: true)`，输出接到
一个**自定义 `Sink`**（`_CappedSink`）上，超限时在 `add()` 里抛。见
`bounded_read.dart` 的 `_inflateRawBounded` / `_decompressBounded`。

**这一条现在有测试守着**：`packages/archive_safety/test/bounded_read_memory_test.dart`
（2 条，按 ΔRSS 断言，阈值 16 MiB）。已实测「退回旧实现 → 该测试红」
（ΔRSS 32.8 MiB），不是写了个永远绿的断言。

### 10.4 A3：Zip64 与 data descriptor（已完成）

**先读源码确认「库支持什么」**（`archive-cb3a07c/lib/src/codecs/zip/`）：

| 事实 | 位置 |
|---|---|
| Zip64 中央目录 extra（id `0x0001`）支持 `uncompressedSize` / `compressedSize` / `localHeaderOffset` / `diskNumberStart` | `zip_file_header.dart:83-98` |
| Zip64 EOCD 记录 + 定位器支持（`0x06064b50` / `0x07064b50`） | `zip_directory.dart:_readZip64Data` |
| data descriptor（flag bit 3）会读 12/16 字节，但**尺寸始终以中央目录为准** | `zip_file.dart:95-96,141-151` |
| 本地头里的尺寸**被中央目录覆盖**（Zip64 下本地头是 `0xFFFFFFFF`） | `zip_file.dart:93-96` |

**但「库支持」不等于「我们的有界读取还有界」** —— 这两个格式恰好都改动了
「尺寸从哪来」：Zip64 把真实值挪进 extra、data descriptor 把真实值挪到数据
之后。闸 1、闸 2 全靠 `ArchiveFile.size` / `ZipFile.compressedSize`。

夹具：`test/fixtures/zip/`（8 个，全部 < 1.2 KiB，由 `tool/make_zip_fixtures.py`
用 Python `zipfile` 生成后按规范改字段；期望值用 `unzip -t` 与 Python `zipfile`
两个外部实现核对，**不从本项目的解析器取**）。

测试：`test/zip_format_support_test.dart`，**16 条**：

| 分组 | 关键断言 |
|---|---|
| Zip64 中央目录 | 512 字节逐字节一致；`file.size == 512`（**不是 0xFFFFFFFF**，否则闸 1 失效） |
| Zip64 EOCD | 136 字节逐字节一致 |
| Zip64 + 小上限 | 闸 1 在解压前拦下 |
| data descriptor | `flags & 0x08 == 0x08`；`compressedSize > 0`；4096 字节逐字节一致 |
| data descriptor + 小上限 | 被拦 |
| 正常条目 | 闸 1 拦下（声明诚实）→ 不浪费一次解压 |
| 前缀读取 | 1 MiB 条目读 4 KiB，**拿满 4096 字节**（见 10.5 的修复） |
| CD 谎报原始大小 | 512 KiB 上限 → `inflate` 拦下，`observed ∈ (512 KiB, 1 MiB]`；2 MiB 上限 → 完整读出 1 MiB |
| CD 谎报压缩后大小 | `corrupt`/`inflate`，**不返回半截内容** |
| 压缩数据是垃圾 | `corrupt`/`inflate`，不抛到调用方 |
| 尾部截断 | 走 `ApkReader.openBytes` → `ArchiveOpenResult.corrupt`（库会抛 `RangeError`，但生产入口兜住了） |
| 共享账本 | 第二条被拒时 `limitBytes == 剩余预算` |
| 诊断文本 | `describe()` 同时含条目名、阶段、observed、limit |

### 10.5 本轮修掉的两个真问题（都是被测试逼出来的）

1. **前缀读取整块丢弃 → 返回 0 字节**。zlib 会把一大块输出**一次**交给
   `writeBytes`；旧实现「超限就整块丢掉再抛」，于是
   `readEntryPrefix(…, maxBytes: 4096)` 得到 0 字节，调用方无法区分「被截断」
   与「条目本来是空的」。
   更严重的是它的**下游后果**：`HardeningScanner._readHeader` 拿到 0 字节后
   返回 `null`，于是**每一个 DEX 都被记成「entry could not be read」** ——
   真实样本上会凭空多出 55 条加固线索，而进度文档里那个「29 ms」其实是
   「什么都没读」换来的。现在按「填满到 cap 再抛」，实测真实样本加固扫描
   41 ms、线索 4 条（1 条多 DEX + 3 条 assets 里的代码文件），**没有一条
   误报**。
2. **`writeStream` 整条物化**。`ZipFile.decompress` 对 STORE 条目走
   `output.writeStream(全部内容)`，而旧实现是 `writeBytes(stream.toUint8List())`
   —— 一次性把整条条目复制成 `Uint8List`，上限完全没拦住。改为 64 KiB 分块搬运。

### 10.7 第 3 部分：安全边界复查（推翻了 §3 的一句错话）

也就是说当时是「知道但没改」，而文档里写成了「没有了」。

| 位置 | 原来 | 现在 |

`ArchiveFile` 兜底**（内容本来就在内存里，按长度判，合理）；`tool/perf_probe_test.dart`

### 10.8 完整性闸（新增）

`readEntryBounded` 增加一条：**产出少于声明值 = 数据被截断，按 `corrupt` 拒绝**。

为什么必须加：把中央目录的 `compressedSize` 改小一半，`archive` 的流式解压
**不报错**，只是提前结束 —— 「返回半截内容」与「返回完整内容」在调用方看来
一模一样。对安全分析尤其危险：半截的 DEX / Mach-O 会被当成完整的来判定。

只判「少」不判「多」：加固包会故意把 `uncompressedSize` 报小（V2.4.10 的
零填充清单），产出多于声明值是**已知的合法形态**。实测 `49af6cnn-1018.apk`
仍然 `open=ok`、6/6 DEX、2 条线索（多 DEX + 100 条诱饵条目）。

## 11. 阶段 B 计划（按优先级；本文件是唯一进度载体）

> 阶段 A 已收尾（§10）。阶段 B 的约束与阶段 A 相同：**先写测试再改实现**、
> **不为了变绿放宽断言或加 Skip**、**不提前重构高级规则**、**不做动态沙箱**、
> **不做 AI 分析**。

### B-1（P0）ToolDownloader：校验和与失败面

**为什么排第一**：它是唯一一条「从网络拿可执行文件并落盘」的路径，而
`tool_downloader.dart` 在阶段 A 之前**全仓零测试**。阶段 A 只补了解包侧的
预算（6 条），校验和、下载中断、版本不匹配、部分写入都还没有断言。

要做：

1. 校验和**不能被绕过**：错误的 sha256 → 拒绝安装且不留文件；正确 → 安装。
2. 下载中断（`http` 抛异常 / 流提前结束）→ 不留下半截 zip，临时文件清理。
3. HTTP 404 / 302 到非预期主机 → 明确失败类型，不退化成「解压失败」。
4. 版本目录已存在但内容损坏 → 重新下载而不是复用。
5. 三态可区分：**下载失败 / 校验失败 / 解包失败**（现在是两种异常类型，
   缺下载失败的独立类型）。

验收：`test/tool_download_failure_test.dart`，每个失败面一条；用本地 HTTP
server（`dart:io HttpServer`）而不是 mock，避免测「我们以为的 http 行为」。

### B-2（P0）XapkInstaller：调用路径安全测试

**为什么**：阶段 A 只覆盖了「预算」这一面。路径安全（`..`、绝对路径、
符号链接、大小写冲突、同名覆盖）在 `xapk_installer` 上还没有端到端测试 ——
`zip_guard` 有单测，但**调用方是否真的走了那条路**没验证。

要做：

1. 恶意条目名（`../x`、`/etc/x`、`a/../../x`）→ 拒绝且不写到目标目录之外。
2. 两个条目解出同一路径（大小写差异 / `a/b` 与 `a//b`）→ 后者不覆盖前者。
3. 符号链接条目 → 当普通文件写，不创建链接。
4. `base.apk` 缺失 / 多个 `base.apk` → 明确失败原因。
5. 临时目录在**所有**失败分支上都被清理（含取消）。

验收：`test/xapk_path_safety_test.dart`；断言用「目标目录树快照」比对，
不只断言返回值。

### B-3（P1）ReportExporter：三态测试

**为什么**：`report_exporter` 全仓零测试，而它产出的是**用户会拿去做判断的
文件**。「字段缺失」「字段读失败」「字段值正常」在报告里必须长得不一样 ——
这是项目里反复强调的三态，但导出侧没有任何断言。

要做：

1. `absent` → 报告里是「-」，不是空串、不是 `null`。
2. `failed` / `wrongType` → 带状态名与原因。
3. 正常值 → 原样（含 CJK、超长字符串、换行）。
4. 同一份数据导出两种格式（JSON / Markdown 或现有格式）时字段集合一致。
5. 报告里不出现 `Instance of ...`、`Closure: ...`（i18n 踩过的坑）。

验收：`test/report_exporter_test.dart`；用「构造的 `AnalysisReport` + 逐字段
断言」而不是快照比对（快照会把错误一起固化）。

### B-4（P1）安全发现模型：是否支持 source / transform / sink / confidence

**为什么**：这是 B-5 / B-6 的前提。现在 `SecurityFinding` 有 code、severity、
evidence，但**没有「数据从哪来、经过什么、到哪去」的字段**，也没有
confidence。如果模型不支持，B-5/B-6 只能靠 evidence 字符串拼，之后一定要
重构。

要做（**只做评估与最小扩展，不重写规则**）：

1. 盘点现有 `SecurityFinding` 的字段与所有构造点（按 `SecurityFinding(`
   结构分块统计，不用正则）。
2. 判断能否用**可选字段**表达 `source` / `transform` / `sink` / `confidence`，
   且不破坏 `withDedupedEvidence()` 这类手工重建点（历史上漏带过 4 个字段）。
3. 产出结论：**能扩展 / 需要新类型 / 不该做**，并给出迁移成本。

验收：一份评估结论 + 若可行则一个最小字段扩展 + 一条「字段有消费者」的测试。

### B-5（P2）Android：DEX Source → Transform → Sink 最小可验证分析

**为什么**：现在的 DEX 分析是「字符串 + 方法引用 + 调用点」三张表，能回答
「用了什么」，回答不了「数据从哪来到哪去」。而这是安全分析的核心问题。

要做（**最小可验证**，不做全量污点分析）：

1. 选**一个**可判定的模式（例如 `getDeviceId()` → `StringBuilder` →
   `HttpURLConnection`），在真实 DEX 上能复现调用链。
2. 用**真实产物**造夹具（`javac` + `d8`），期望值用 `dexdump` 独立核对。
3. 输出必须带「证据位置」（方法 + 偏移），且**不确定时说不确定**
   （confidence 或 `unknown`），不许猜。
4. 误报优先于漏报控制：宁可只报一条确定的，不报十条可能的。

验收：`test/dex_dataflow_test.dart` + 一条真实样本上的端到端断言。

### B-6（P2）IPA：相册 / OCR / 敏感数据 / 网络 证据关联

**为什么**：IPA 侧现在有 `PrivacyInfo.xcprivacy`、权限描述、Mach-O 符号三份
材料，但**彼此不关联** —— 声明了相册权限、代码里没有相册 API，这种矛盾
正是最有价值的信号，现在报不出来。

要做：

1. 建立「声明（Info.plist / xcprivacy）↔ 实现（Mach-O 符号 / 字符串）」的
   对照表，**只报有证据的矛盾**。
2. 每条矛盾要能指到具体符号或具体声明键。
3. 「查不到」与「没有」必须分开（`absent` vs `failed`）。
4. 夹具用真实 IPA 的裁剪版（`sun_signed.ipa` 里已经有 27 个嵌套 bundle）。

验收：`test/ipa_evidence_correlation_test.dart` + 真实 IPA 上的端到端断言。

### 顺序理由

B-1 / B-2 是**已有代码的安全网**（零测试的路径先补网，成本最低、风险最高）；
B-3 是**用户直接看到的东西**；B-4 是 B-5 / B-6 的**模型前提**，必须先定；
B-5 / B-6 是**新能力**，放在模型稳定之后，否则一定要返工。

### 13.3 模型：`dataTransform`

`packages/analysis_model/lib/src/security_finding.dart`：

```dart
/// 来源与去向之间的**中间跳**（处理环节）；没有则为 `null`。
final String? dataTransform;
```

三条约束写进了文档注释：

1. **自由文本而不是结构化 hop 列表** —— 静态分析能确定到「哪个方法」这一级，
   确定不到「哪个寄存器、哪次赋值」。做成 hop 数组会让人以为逐跳都验证过了。
2. 与 `relationship` 分工：`dataTransform` 是**机器可读的定位**（能拿去搜代码），
   `relationship` 是**给人读的说明**（含「哪一段没证实」）。
3. `withDedupedEvidence()` **必须透传** —— 这个方法每条发现都会过，历史上漏带过
   四个字段。测试里专门造了「有重复证据」的样本强制走重建分支来钉它。

### 13.4 规则：`ANDROID-RULE-C` 填中间跳

`coOccurrenceNote()` 的返回值多了 `caller`：

| 分支 | `relationship` | `dataTransform` |
|---|---|---|
| 同一方法体 | 含 `in the same method body`，并点出方法名 | **该方法完整签名**，如 `Lcom/example/fixture/Pipeline;.run(Ljava/lang/String;)V` |
| 整包层面 | 含 `not in the same method body` | **`null`** |

整包层面留空是刻意的：那里根本没有「中间跳」的证据，填一个「大概是这里」
就是把猜测写成事实。测试里正反两个样本都钉住。

## 14. 阶段 B 第三轮：B-6 完成（iOS 证据关联的反方向）

> **不升版本、不打 tag、不提交。**

### 14.1 一句话结论

iOS 侧原本只有「有实现、没声明」这一个方向（会崩、会被拒）。B-6 补上**反方向**：
「声明了用途说明、但扫描范围内找不到对应 API 线索」—— 抓的是**过度声明**
（从模板复制来的 `NSPhotoLibraryUsageDescription` 之类）。新增 **18 条测试**。

过程中真实样本抓到一个**误报**，已修（见 14.4），这条比新功能本身更值得记。

### 14.2 先看清现状，避免重复造

核查后发现 iOS 侧已经有相当完整的隐私审计（`IosPrivacyAudit`，1142 行）：

| 已有 | 说明 |
|---|---|
| `IOS-USAGE-DESCRIPTION` | 逐条记录 Info.plist 的用途说明（info/confirmed） |
| `IOS-PHOTO-LIBRARY-NO-USAGE` / `IOS-CAMERA-NO-USAGE` | **有实现、没声明** → P2 |
| `IOS-PHOTO-PICKER` / `IOS-RULE-A/B/C/D/E/F` | 选择器 vs 完整库、OCR、上传链路等 |
| `IOS-SCAN-COVERAGE` | 覆盖了 N 个可执行文件中的 M 个 |

**缺的正是反方向**：声明存在、却没有对应线索时，报告只留一句「请自行与 API
线索对照」。读者要自己去比对两条互不相邻的发现项 —— 这等于没做关联。

### 14.3 新规则：`IOS-USAGE-WITHOUT-API`

| 项 | 取值 | 理由 |
|---|---|---|
| 触发 | 有 `NSPhotoLibrary*` / `NSCamera*` 用途说明，且**没有任何**对应线索 | |
| 等级 | `info` | 这是「值得看一眼」，不是「有问题」 |
| 置信度 | `unknown` | 「没有符号」**不能**推出「没有这个功能」 |
| 证据 | Info.plist 的键与原文 + 「哪些标记都没命中」 | 可复核 |
| 扫描范围 | 写进正文，如 `main executable + 24 nested executable(s)` | 读者要知道「没找到」是在多大范围里得出的 |

三条边界写在代码注释与测试里：

1. **`PHPickerViewController` / `PhotosPicker` 都算「有实现」** —— 系统选择器是
   跨进程的，不需要相册权限，但它确实是相册输入路径；
2. **没读到可执行文件时不判** —— 那是覆盖不足，不是矛盾；
3. **扫描被预算截断时不判** —— 线索可能在截断之后（这条是被真实样本逼出来的）。

### 14.4 真实样本抓到的误报（本轮最重要的发现）

第一版在 `sun_signed.ipa`（40.5 MB）上跑出：

```
IOS-USAGE-WITHOUT-API [info/unknown] {key: NSCameraUsageDescription,
                                      scope: main executable + 24 nested executable(s)}
```

但直接在这份二进制里搜 `AVCapture` 是**存在**的。原因是扫描预算
`_Budget.maxBytes = 16 MiB`，而主可执行文件 45 MB —— `AVCapture` 出现在
16 MB 之后，**没被扫到**。规则把「我们没看到」写成了「应用没实现」。

修法：`if (scannedAnyExecutable && !truncated)`。修完再跑，发现项从 11 条回到
10 条，误报消失。

**这条用单测抓不到**：构造 16 MB+ 的夹具才能覆盖，而且先得知道预算值。
它是「真实样本回归」抓到的 —— 也正是为什么每次改规则都要跑一遍真实样本。

回归用例已补：17 MB 的字节数组、`AVCapture` 放在最后 9 字节，断言不产生发现项。

### 14.5 顺带修的一个同类问题

`nestedExecutables` 在生产路径里包含**读失败**的条目（`bytes == null`），用来算
覆盖率。第一版用 `nestedExecutables.isNotEmpty` 判「扫过」，于是「全部读失败」
也会被当成扫过 → 同样误报。改为只数 `bytes != null` 的，并补了用例。

### 14.6 i18n：新 code 必须注册到四个 switch

`AnalysisReport` 的 `findingText` / `recommendationText` / `relationshipText` /
`limitationText` 都是**显式 switch**（不是按 code 自动拼 key）。漏注册的后果是
**静默回退英文**：编译通过、中文界面照常显示英文句子。本轮第一次跑测试就是
这样红的（三个断言同时报英文原文）。

四个 code 全部注册，并在测试里加了一条**直接读 4 个语言包 JSON** 的守卫：
跑一次审计，把它产出的每个 `messageCode` / `recommendationCode` /
`relationshipCode` / `limitationCode` 都映射成键名（`.` → `_`）逐个核对存在。
这比逐条 grep 可靠 —— 也是记忆里「改文案要按所有语言包扫一遍」那条的正确做法。
