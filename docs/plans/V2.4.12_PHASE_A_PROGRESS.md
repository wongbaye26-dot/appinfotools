# V2.4.12 — 阶段 A：实际解压量限制与归档安全边界整改

> 用户任务书：`AppInfoTool 安全分析增强 — 阶段 A`。
> 起点：`main` @ `e2cc356`（tag `v2.4.11`），工作区干净。
> 本轮**只做归档安全基础**，不新增风险规则、不做动态沙箱、不做 AI 分析。

---

## 0. 一句话结论

**V2.4.11 记的「做不到有界解压」是错的。** 我当时读的是 **pub.dev 的
`archive 3.6.1`**，而本项目实际用的是 **git 依赖**（`ref cb3a07c`）——
后者有 `ZipFile.decompress(OutputStream)`，是**真正的流式**接口。
给它喂一个带上限的 `OutputStream`，超限时在写那一块时抛异常，zlib 就地停下。

实测（5 MiB 全零条目，上限 1 MiB）：在 `observed = 1,067,098` 处抛出，
**已产出 1,001,562 字节就中止**，从未物化 5 MiB。

## 1. 变更模块与原因

| 模块 | 改动 | 为什么必须改 |
|---|---|---|
| `packages/archive_safety/lib/src/bounded_read.dart` | **新增**（约 380 行） | 有界解压的唯一实现：`ByteSource` 不需要了（`archive` 已物化压缩字节），核心是 `_CappedOutputStream` + `readEntryBounded` / `readEntryPrefix` + `BoundedReadLedger` + `BoundedReadFailure` |
| `packages/archive_safety/lib/src/zip_budget.dart` | `readEntry` 改为委托；`check` 增加**压缩后大小**两道 | 原来只查解压后声明值，压缩后大小无边界 |
| `packages/apk_parser/lib/src/apk_reader.dart` | `readFile` 传共享 ledger；manifest / arsc 改走有界读取 | 这三处此前都是 `file.content`（**无上限**） |
| `packages/apk_parser/lib/src/hardening.dart` | `_readHeader` 改 `readEntryPrefix(64 KiB)` | 此前为了看 8 字节把整条 DEX 解压一遍（343 MB 包实测 **30ms → 896ms**），且无上限 |
| `packages/ipa_parser/lib/src/ios_signature.dart` | `CodeResources` 改有界读取 | 此前是「先 `entry.content` 再比长度」 |
| `lib/utils/zip_helper.dart` | `readFileContent` / `extractFile` 传共享 ledger | IPA 读取与 XAPK 解包落盘都经过这里 |
| `lib/utils/zip_guard.dart` | `extractToDirectory` 改有界读取，超限抛 `ZipBombException` | 工具下载（platform-tools / build-tools）解包落盘此前无上限 |

**没有重写解析器，没有升级依赖。**

## 2. 三道闸与共享预算

`readEntryBounded(file, maxEntryBytes, ledger)`：

| 闸 | 判据 | 行为 |
|---|---|---|
| 1 | `file.size`（**声明**解压大小） | 超限 → **不解压就拒绝** |
| 2 | `file.rawContent.compressedSize`（**声明**压缩大小） | 超限 → 连原始数据都不读 |
| 3 | **解压过程中真实产出** | 逐块写，超限的那一块抛异常 → **就地中止** |

- 单条目上限：**256 MiB**（`maxSingleEntryUncompressed`，未变）。
- 单条目压缩上限：**512 MiB**（`maxSingleEntryCompressed`，新增）。
- 一次读取流程的**真实产出**总量：**1 GiB**（`maxSessionOutputBytes`，新增）。
- 一次流程的**压缩**总量：**2 GiB**（`maxTotalCompressed`，新增）。

**共享预算**：`BoundedReadLedger` 由 `ApkReader` / `ZipHelper` / `ZipGuard`
各自持有，一次 `open` 一个；嵌套归档共用同一个实例 —— 子归档**拿不到**完整
独立配额（`test/bounded_read_test.dart` 的「嵌套归档共享预算」用例钉住这条）。

**超限诊断**：`BoundedReadFailure{entry, stage, observedBytes, limitBytes}`，
`describe()` 输出 `classes.dex: stopped at inflate after 1067098 bytes
(limit 1048576)` —— 条目、阶段、实际字节三项齐全。

## 3. 全部读取 / 解压入口（逐条核实）

| 入口 | 用途 | 状态 |
|---|---|---|
| `ApkReader.readFile` | APK 的 DEX / manifest / arsc / so | ✅ 有界 + 共享 ledger |
| `ApkReader.parse`（manifest / arsc） | 解析入口 | ✅ 有界 |
| `ApkReader.openBytes` | 嵌套归档 | ✅ 有界（每次重置 ledger） |
| `ZipHelper.readFileContent` | IPA 读取 | ✅ 有界 + 共享 ledger |
| `ZipHelper.extractFile` | XAPK 解包落盘 | ✅ 有界 + 共享 ledger |
| `ZipGuard.extractToDirectory` | 工具下载解包落盘 | ✅ 有界 + 单次流程共享 ledger |
| `HardeningScanner._readHeader` | DEX 魔数嗅探 | ✅ 有界**前缀**读取（64 KiB） |
| `IosSignature` 的 `CodeResources` | 签名材料 | ✅ 有界 |
| `ZipBudget.ensureWithin` | 工具下载前置校验 | 不变（声明级） |

**`file.content` 在 `lib/` 与两个解析器里已经没有任何调用点**
（`grep -rn "\.content"` 只剩 `FileContent` 类型声明与 DER/CMS 的局部字段）。

## 4. 技术限制与选型（任务书第 10 条）

**结论：现有归档库支持安全的有界流式输出，因此没有「解压后再检查」的伪装。**

关键事实（读的是**实际依赖**的源码，不是 pub.dev）：

| 事实 | 位置 |
|---|---|
| `ZipFile.decompress(OutputStream)` 把 zlib 输出逐块写进调用方的 `OutputStream` | `archive-cb3a07c/lib/src/codecs/zip/zip_file.dart:164` |
| `OutputStream` 是**导出的抽象类**（`length` / `clear` / `flush` / `writeByte` / `writeBytes` / `writeStream` / `subset`） | `lib/src/util/output_stream.dart:7`，导出见 `lib/archive.dart:53` |
| 压缩字节在 `ZipFile` 构造时已物化（`readBytes(compressedSize)`） | `zip_file.dart:105` |

**被否决的备选方案**：

1. **自解析 local file header + `ZLibDecoder` 接上限 `Sink`** —— 可行（已用探针
   验证：`header.localHeaderOffset` 公开、`dart:io` 的 `ZLibDecoder` 接
   `Sink` 能中止），但要自己处理 Zip64 / data descriptor，代码量远大于
   `decompress(OutputStream)`，**没有必要**。
2. **`Inflate.stream` + `inflateNext`** —— 该 API 在本 git 版本里也存在
   （`lib/src/codecs/zlib/inflate.dart`，已导出），但 `decompress` 已经封装好
   了分块循环，直接用更省事。
3. **提高压缩比阈值 / 只做后置长度检查** —— 前者被 V2.4.10 证伪（229:1 vs
   205:1 无法区分），后者就是 V2.4.11 的临时方案，**峰值内存仍不受限**，本轮
   明确不采用。

## 5. 测试矩阵（任务书列出的 10 类，全部小样本 / 小预算）

`packages/archive_safety/test/bounded_read_test.dart`（**13 条**）：

| 任务书要求 | 用例 | 关键断言 |
|---|---|---|
| 正常归档 | 预算内正常读出 | 内容逐字节一致 |
| 声明 < 实际 | 声明 1 KiB / 实际 256 KiB | `stage == inflate`；`bytes == null`；`observed > cap` 且 `< real` |
| 单条目超限 | 声明 1 KiB / 实际 512 KiB，cap 8 KiB | `observed < real / 2` —— **中止点接近上限，不是条目大小** |
| 多条目累计 | 3 × 6 KiB，ledger 16 KiB | 第三条被拒；`produced ≤ 16 KiB` |
| 嵌套累计 | 外层 6 KiB 后内层只剩 2 KiB | `limitBytes == 2 KiB`（**不是完整配额**） |
| 压缩输入过大 | CD 的 compressedSize 改 1 GiB | `check` 返回 `compressed bytes` 违规 |
| 中途解压失败 | 压缩流截断 | `corrupt` 或产出 ≠ 声明 |
| 重复条目 / 异常路径 | 同名条目两条 | 取第一条、不崩 |
| 合法大量零填充 | 2 MiB 全零，cap 4 MiB | **通过**（V2.4.10 兼容性） |
| 拒绝时不返回超限内容 | 上述各拒绝用例 | 一律 `bytes == null` |

外加：加密条目 → `unsupported`（**拒绝而不是退回无界读取**）；
内存合成 `ArchiveFile` → 按声明值判。

**没有一条用例依赖大型真实恶意样本，也没有触发不受控的内存分配**
（最大样本 2 MiB，最大单次断言预算 64 KiB）。
