# AppInfoTool V2.4.9 — 「覆盖不足」面板的诊断

> 用户问：「分析里的覆盖不足是什么原因导致的？能解决吗？」
>
> 结论先行：**分析结论没错，是这个面板本身有问题** —— 一半是「我们自己的
> 预算上限」，一半是「这个包被加固过」，还有几条是**文案缺陷**（说不出数字、
> 带 Markdown 标记、漏代码标识符）。文案缺陷本轮已修；预算上限实测**不值得
> 调**；加固证据的本地化留到下一轮。

---

## 1. 这 11 条分别是什么

样本：`腾⤑⨪讯⌳视␢频-v3.20.apk`（`classes.dex` = **17,534,446** 字节，
与用户截图里的数字完全一致；171 个诱饵条目）。

| # | code | 性质 |
|---|---|---|
| 1 | `android.dex.budget` | **我们主动设的上限**（8 MiB / 单文件） |
| 2 | `android.dex.scan_summary` | 静态分析边界（只提取 ASCII 字符串） |
| 3 | `android.dex.method_semantics` | 静态分析边界（不做数据流） |
| 4–8 | `android.container.anomaly` ×5 | **这个包被加固过**的事实 |
| 9 | `android.native_symbols.semantics` | 静态分析边界（不反汇编） |
| 10 | `android.offline_static_analysis` | 静态分析边界（不运行） |
| 11 | `android.analysis.based_on_cooccurrence` | 静态分析边界（同现启发式） |

**没有一条是「解析失败」** —— 第 4–8 条恰恰说明解析器**读到了**这些结构
（159 个诱饵条目、`attributeStart` = 343、`attributeSize` = 26、namespace
chunk 1476、未知 chunk `0x0200` 都读出来了），只是如实标注「结构不标准」。

## 2. 第 1 条（预算）到底卡掉了多少：实测

`DexClueScanner.maxBytesPerDex = 8 MiB` / `maxTotalBytes = 48 MiB`。
把两个上限做成参数后逐档实测：

### 加固包（腾讯视频，1 个 DEX 17.5 MB）

| 每文件上限 | 耗时 | 实际扫 | 线索 | 域名 |
|---|---|---|---|---|
| 8 MiB（现状） | 26 ms | 8,388,608 | **0** | 0 |
| 16 MiB | 61 ms | 16,777,216 | 0 | 0 |
| 32 MiB（整份） | 56 ms | 17,534,446 | **0** | 0 |

**多扫 9 MB，一条新线索都没有。** 原因很直接：这是加固包，真正的代码被壳
加密了，明文字符串本来就不在里面。

### 抖音（55 个 DEX，合计 437 MiB）

| 上限 | 耗时 | 覆盖 | 线索 | 跳过 |
|---|---|---|---|---|
| 8 MiB / 48 MiB（现状） | 1.77 s | 7 个 DEX / 48 MiB | **11** | 51 |
| 8 MiB / 128 MiB | 5.34 s | 19 个 DEX / 136 MiB | **14** | 44 |
| 32 MiB / 256 MiB | 10.06 s | 33 个 DEX / 261 MiB | **14** | 22 |

**代价 8 秒，多 3 条线索；而且 55 个 DEX 仍然只覆盖 33 个。**

### 结论：不调预算

V2.4.7 刚把大包解析从 64 s 压到 13.5 s，为了 3 条线索加 8 秒不划算。
真正划算的做法（**下一轮**）是**改扫 DEX 的 `string_ids` 字符串池**而不是
原始字节 —— 字面量只存在于字符串池，扫池子是「100% 覆盖 + 读的字节更少」。

## 3. 第 4–8 条：不是 bug，是这个包被加固了

| 现象 | 说明 |
|---|---|
| 159 entries use a file entry as a directory prefix | 诱饵条目：`AndroidManifest.xml/..xml`、`resources.arsc////.xml`。**专门用来打断「按路径解包」的朴素提取器** |
| `attributeStart` 343（标准 20） | 清单被改过布局；按固定偏移读的解析器会一无所获 |
| `attributeSize` 26（标准 20） | 同上 |
| namespace chunk 1476（标准 24） | 同上 |
| 未知 chunk `0x0200` | 标准 AXML 的 chunk 类型里没有它 |

**这些不该被「修掉」**：它们是加固线索，删掉等于把「这个包不正常」藏起来。

**剩下的缺陷是语言**：这 5 条的正文是加固扫描器拼出来的英文证据
（`'${count} entries use a file entry as a directory prefix, e.g. $samples'`
这类）。要本地化，得把加固证据也改成**结构化数据**（`code` + 参数），
涉及 `ManifestLayoutAnomalies` / `HardeningObservation` / `containerAnomalies`
三处的模型 —— 属下一轮。本轮**未做**。

## 4. 本轮实际改了什么（文案缺陷）

1. **预算那条说不出数字**。`DexScanResult.skippedForBudget` 从「一句拼好的
   英文」改成 `List<DexBudgetSkip>`（名字 / 已扫字节 / 总字节 / 覆盖率），
   界面现在能说「只扫描了前 8388608 字节（文件共 17534446 字节，约 47%）」。
   - 覆盖率**向下取整、且部分扫描绝不给 100%**：一个只比上限大 22 字节的
     DEX，`round()` 会算出 100%，而它恰恰是「未覆盖」的那一条。
2. **两条说明里的 `**`（Markdown）** 在纯 `Text` 里原样显示 —— 去掉，改用措辞。
3. **`includesRuntimeEvidence` 漏进了正文** —— 改成「因此不存在任何运行时证据」。

### 踩到的两个坑

- **`analysis_diagnostic` 与 `security.limitation_notes` 是两个分组**：这个
  面板走的是后者（`AnalysisReport.limitationNoteText`），我一开始把文案加进了
  前者，全是死键 —— 已撤回。
- **`invalid_override`**：给 `android_dex_budget` 加了三个占位符之后，ja / ko
  的旧签名（只有 `name`）直接编译失败。**加占位符必须同时改所有语言包**。

## 7. 补充：IPA 侧（用户第二轮指出）

用户随后贴了 IPA 的同一个面板，问题**同类但更明显**：

| 现象 | 原因 | 处理 |
|---|---|---|
| `4 个可执行文件未参与扫描（Payload/…/App（bytes not retained (nested budget of 32 MiB reached)））` | 未扫描清单把引擎侧的 `bytesFailure`（英文句子）拼进了 `names` 参数 | **只列路径**。原因在 `IosNestedBinary.failure` / 详情页嵌套清单 / 解析诊断里仍然能看到 |
| `运行时证据（includesRuntimeEvidence）恒为 false` | 模型字段名漏进文案（**iOS 侧也有，V2.4.9 第一版只改了 Android**） | 改成「因此不存在任何运行时证据」，六个语言包全改 |
| `它说明二进制**导入**了哪些系统能力` | `**` 是 Markdown，界面是纯 `Text` | 去掉。**ja/ko 里还有 2 条第一版漏掉的**，一并清掉 |

**第一版为什么漏**：我只按 zh-CN 的扫描结果修，而 ja/ko 的键集与措辞不完全相同
（`android_dex_method_semantics` / `android_native_symbols_semantics` 在 ja/ko
里也带 `**`）。**教训：改文案要按「所有语言包」扫一遍，不能只看 zh-CN。**

### 新增守卫

`test/limitation_notes_test.dart` 增加一条**直接读 6 个语言包 JSON** 的检查：
`security.limitation_notes` 的每一条都不得含 `**`、不得含
`includesRuntimeEvidence`。已实测验证它真的会红（往 zh-CN 注入一个 `**` 后
立刻失败）。

`test/ios_privacy_audit_test.dart` 增加一条：未扫描清单的 `names` **每一条**都
必须是纯路径（不含中文括号、不含 `bytes not retained` / `budget`）。

### 顺带修的偶发失败

`test/rename_dialog_test.dart` 的「合法名字真的改名」在**全量跑**时偶发超时
（单独跑 3/3 通过）。原因是它的轮询上限卡在 50 × 10ms = 500ms，而
`flutter test` 同时跑几十个 isolate 时真实事件循环会被饿住。上限放宽到
300 × 10ms（3 秒），一旦拿到结果立刻退出 —— 正常路径不受影响。
