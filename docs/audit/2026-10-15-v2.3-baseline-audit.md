**归档安全**
- `ZipBudget`：总解压量 1 GiB / 条目数 100000 / 压缩比 100（> 16 MiB 时校验）/ **负尺寸拒绝**（`zip_budget.dart:16-56`）
- `ArchiveOpenResult` **五态**：`ok` / `notArchive` / `corrupt` / `resourceBudgetExceeded` / `ioError`（`archive_open.dart:14-44`）
- 路径穿越防护在应用层 `ZipGuard.safeJoin`：拒绝绝对路径 / `~` / 盘符 / 逐段 `..` / 规范化后越界（`zip_guard.dart:22-49`）
- **符号链接一律当普通文件写、绝不落盘建链**（`ipa_bundle_extractor.dart:202-204`）

**应用层与报告**
- 双解析流水线：Android worker isolate（`parse_task.dart:176`）、iOS worker isolate（`ipa_parse_task.dart:144`）
- 安全结果全链路贯通：`ParsedApkData.security` → `ApkInfo.securityResult` → `FileState` → `PackageAnalysisResult.security` → UI/报告
- **真取消**：`CancellableParseTask` 抽象；isolate `Isolate.immediate` 强杀、aapt2 子进程 `SIGKILL`、iOS 解包协作式标志
- **报告与 UI 同源**，导出**不重扫**（`export_report_dialog.dart:51-91` 只做渲染 + 写文件）
- Markdown 报告含**字段状态/来源列**与专门的「未执行 / 无法确认」章节（`analysis_report.dart:363-403`）
- 解析阶段由解析器**真实上报**，非定时器编造（`ipa_analysis.dart:9-11` 明确声明「只报阶段、不报百分比」）
- 测试覆盖：安全规则、报告导出、归档安全（含 ZIP Bomb 与 Zip Slip）、真实样本（`APPINFOTOOL_SAMPLES`）、`codesign` 真实输出

## 4. 与规格书的差距矩阵

| 规格书章节 | 要求 | 现状 |
|---|---|---|
| §3.1 Manifest | `maxSdkVersion` / `uses-permission-sdk-23` / 四类组件 / `exported` / 组件权限 / authority | ✅ 已实现（缺 intent-filter 明细与 `enabled`） |
| §3.2 资源表 | 多语言 / 多密度 / 夜间模式 / 自适应图标 / 环检测 / 深度限制 | ⚠️ 缺夜间模式、环检测、包内深度限制 |
| §3.3 分包 | Base 识别 / 分包清单 / **一致性校验** / 覆盖统计 | ⚠️ 缺一致性校验与覆盖统计；**且不跑安全审计（D1）** |
| §3.4 DEX | 结构 → 指令 → 关联，三阶段 | ❌ 仅字符串扫描 |
| §3.5 原生库 | ELF 结构 / 动态符号 / 导入函数 | ❌ 仅统计文件名 |
| §4.1 Bundle | 5 类 / 逐 Bundle 覆盖统计 | ⚠️ 分类齐全，覆盖统计只到主应用 |
| §4.2 Plist | XML + binary / 六态状态 | ✅（缺 `UIBackgroundModes`、`CFBundleURLTypes`） |
| §4.3 Mach-O | Load Commands / 符号表 / 切片 / 截断记录 | ⚠️ Load Commands 与切片齐全，**缺符号表** |
| §4.4 隐私与签名 | PhotoKit 与 Picker 分离 / 材料与验证分离 | ✅ 分离到位（缺 `NSPrivacyAccessedAPITypes`） |
| §5.1 统一阶段 | 各阶段记录输入 / 状态 / 数量 / 规则集 | ❌ 无阶段级统计结构 |
| §5.2 检测范围 | A 照片 / B OCR / C 上传 / D 网络配置 | ⚠️ Android 全有；iOS 缺规则 A/B/E |
| §5.3 规则引擎 | 规则 A–F，**结构化可配置** | ⚠️ Android A–F 全有但**硬编码 if 链**；iOS 缺 A/B/E |
| §5.4 覆盖统计 | 按模块统计覆盖 / 跳过 / 失败 | ❌ 只有自由文本 `limitations` |

1. DEX 与 Mach-O 均为**静态字符串/结构分析**，不是反汇编，不建立完整调用图。

5. 资源表不解析夜间模式；Mach-O 不解析符号表；原生库不做 ELF 解析（阶段 2–4 补齐）。
6. 归档层预算只统计**声明尺寸**，头部少报时无法阻止分配。

### 阶段 4：原生库符号 —— **已完成**

提交 `f295139`。测试 744 → **795 通过 / 11 跳过**。

补上了 DEX 与 Objective-C 层都看不到的一块：**C/C++ 代码**不经过 Java 运行时、
也不经过 Swift 运行时。原生库的符号表（ELF `.dynsym` / Mach-O `LC_SYMTAB`）
能回答「这个二进制导入了哪些系统能力」，而符号名是**精确的标识符**。

| 平台 | 新增 | 独立基准 |
|---|---|---|
| Android | `apk_parser/src/native/elf.dart` + `security/native_symbol_scanner.dart` | NDK 的 `llvm-readelf` / `llvm-nm` |
| iOS | `ipa_parser` 的 `LC_SYMTAB` 解析 + `security/ios_native_symbol_audit.dart` | `otool -l` / `nm` |

**标记表移到 `analysis_model`**：`system` / `dlopen` / `ptrace` 在两端是同一套
libc 名字，两边各写一份必然漂移 —— 与 `codeMarkers` 是同一条教训。

**本阶段实测确认的一处关键事实**：Mach-O 的 `symoff` / `stroff` 是相对
**切片起始**的，不是相对整个文件。证据是 fat 里 arm64 切片的 `symoff` 与
thin arm64 完全相同（33112），而它在文件里的起点是 16384。按文件绝对偏移
解释会解出垃圾 —— 有测试专门钉住，反向验证会失败。

**预算策略**：`selectLibraries` 在**读取之前**决定分析哪些库，并且
**按库名去重、同一个库只取一个 ABI**（优先 arm64-v8a）。同一个库在 4 个 ABI
下导入的符号几乎一样，全部分析等于把预算花在重复内容上。
为此给 `ApkReader` 加了 `listFilesWithSize` —— 预算必须在读取之前判定。

**新增发现项** `ANDROID-NATIVE-SYMBOLS` / `IOS-NATIVE-SYMBOLS`：
命令执行 / 动态加载 / 反调试给 p3，纯网络能力给 info；置信度一律
`independentCapability`。措辞守住三条界线（有能力 ≠ 调用过；
未反汇编；仅凭导入 `system` 不算风险判定）。
