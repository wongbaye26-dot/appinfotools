## 2. 验收口径

质量门与 CI 一致（见 `.github/workflows/build.yml` 的 `quality` job）：

```sh
flutter pub get --enforce-lockfile
dart run build_runner build --delete-conflicting-outputs
dart format --output=none --set-exit-if-changed $(git ls-files -co --exclude-standard '*.dart')
flutter analyze --fatal-infos --fatal-warnings
for pkg in packages/*/; do (cd "$pkg" && dart analyze --fatal-infos --fatal-warnings); done
flutter test
```

三点必须说明：

1. **格式检查用 `$(git ls-files -co --exclude-standard '*.dart')` 而不是 `.`**：
   生成物的格式化风格与 SDK 的 `dart format` 不一致（构造器初始化列表缩进、
   `=>` 换行），扫全树会永远失败。用 `-co` 而不是 `-c`：**新增但还没 `git add`
   的文件同样要被检查** —— 只用 `-c` 会漏掉它们。
2. **`flutter test` 必须设 `NO_PROXY=127.0.0.1,localhost,::1`**，否则环境代理会
   劫持 `flutter_tester` 的本地 WebSocket。
3. **门禁命令不接管道**。`dart format ... | tail -1` 会把退出码换成 `tail` 的 0，
   「格式检查未通过」被吞掉 —— 本次工作因此带着一个未格式化的文件提交过一次
   （`6026f39` 补的）。

**干净检出是必做的一步**：本地工作区会骗人。`.gitignore` 漏掉的夹具、
没跑 format 的文件、未入库的生成物，都只有干净检出才暴露。

## 4. 性能基线

`test/acceptance_test.dart` 把实测值**打印出来**作为后续改动的基线。
阈值（5000 ms / 50 次）刻意宽松：它的作用是抓**病态回归**（例如某次改动把
O(n) 变成 O(n²)），不是卡性能 —— 卡太紧会在负载高的 CI 上变成随机失败。

```
[PERF] DEX 全流程 × 50 = 14 ms （300 个调用点）
[PERF] ELF 结构 + dynsym × 50 = 4 ms（1150 条符号）
[PERF] Mach-O fat 解析 × 50 = 7 ms（100 条符号）
[PERF] 归档预算判定 × 50 = 0 ms
```

「DEX 全流程」= `DexStructure.read` + `DexMethodTable.forEachReference` +
`DexMethodBodies.walk`，即结构、方法引用、调用点三层各跑一遍。

## 7. 未验证项与未实现项

**这一节不粉饰。** 下列事项在本次验收中**没有跑过**或**没有实现**，
逐条写明原因。

### 7.1 未在本机验证（需要 CI 或带样本的环境）

| 事项 | 原因 |
|---|---|
| **真实样本的端到端**（加固 APK、签名 IPA） | 需设 `APPINFOTOOL_SAMPLES=/tmp/samples`，本机未设 → **11 项测试跳过**。样本本身不进版本库（体积大且属于用户数据）。 |
| **交互路径**：拖放、取消解析、导出报告 | 同上，依赖真实样本。单元层面已覆盖（`pending_open_request_test` / `parse_task_test` / `analysis_report_test`）。 |
| **跨平台构建**（macOS / Windows / Linux） | 本机跑不了 `flutter build macos`：`xcodebuild` 解析 SPM 依赖时报 `sandbox-exec: sandbox_apply: Operation not permitted`（当前进程上下文禁止创建 `deny default` 风格的沙箱）。Windows / Linux 构建同理。**只能靠 CI 的 runner。** |
| **「超时后无残留子进程」** | 沙箱不允许枚举进程（`ps` 报 `Operation not permitted`），断言在本机未真正执行。代码已改用 `Process.start` + 显式 kill，但 kill 只及直接子进程（`apksigner` 是启动 java 的脚本，孙进程可能短暂存活）。 |

### 7.2 未实现（已记录在代码里）

| 事项 | 现状 |
|---|---|
| **规则引擎仍是硬编码 `if` 链**（规格 §5.3 要求「结构化可配置」） | 规则 A–F 两端齐全，但规则本身写在代码里，不是数据。改规则要改代码。 |
| **`NSPrivacyAccessedAPITypes` 未解析**（规格 §4.4） | 已核实：代码里没有任何引用。`PrivacyInfo.xcprivacy` 只解析了跟踪域与收集的数据类型。 |
| **`getAllResources` 不收集 style / array 袋里的引用** | 实测 style 里的 `@color/bg` 没进 `references`，因此**经由 style 间接形成的环查不到**。补它要改 `getAllResources` 的输出，而那会同时改变图标渲染器的取数 —— 按「不改无关功能」的约束**未动**，只记录。 |
| **`Assets.car` 里的图标不提取** | 那是 CoreUI 的 BOMStore，图像载荷是 LZFSE 压缩（`bvx2` 块），需要 LZFSE 解码器。bundle 里直接存在的 `AppIcon*.png` 已能解（含 CgBI）。 |
| **aapt2 / XAPK 路径不可取消** | 仍走 `Process.run`，未接入 worker isolate。 |

### 7.3 已写入代码的局限（不是缺陷，是能力边界）

- **DEX 指令遍历的「末尾自检」是必要但非充分条件**：宽度偏大若恰好重新对齐
  （1 跨到 3、长度正好 3），遍历仍落在末尾却漏读一条指令。主力防线是
  「101 条指令偏移与 `dexdump -d` 逐个对照」。
- **`invoke-custom` 引用 `call_site_ids` 而非 `method_ids`**，**不在**调用点
  覆盖范围内（已单独计数并进覆盖说明）。
- **原生库符号分析只到「导入」层面**：未反汇编，因此不知道这些函数在哪些
  代码路径上被调用；经 `syscall()` 直接发起系统调用的实现不出现在符号表里。
- **iOS `-stripped` 的共享库仍保留外部符号**：导入是链接期必需的、导出是对外
  接口，`strip` 都去不掉 —— 因此「没剥离」这条事实对共享库意义有限。
- **归档层预算只统计声明尺寸**：ZIP 头部少报尺寸时无法阻止分配，
  只能在读完后复核并拒绝解析。
